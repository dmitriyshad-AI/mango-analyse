## A. AMO

1. Сохранить работающее продолжение endpoint при совпавшем anchor: прежние
   строки, верхняя граница и следующая страница. Сбой leads не обнуляет
   events/tasks/contacts. Сохранять результат каждого endpoint атомарно в
   существующем checkpoint, даже если следующий endpoint завершился ошибкой.
2. При несовпавшей границе сохранять исходный upper_bound и агрегаты отличий:
   состав ID, порядок, имена изменённых полей. Не расширять окно до now и не
   запускать автоматически те же200страниц без способа завершения.
3. Для такого endpoint завершать фиксированные временные поддиапазоны через
   существующий fetch. Начальная порция не более суток; при cap уменьшать
   диапазон, не поднимать сетевой бюджет. Подтверждённые диапазоны и строки
   сохранять в том же checkpoint. Неподтверждённые старые строки не выдавать
   за проверенную полноту. Новые поля checkpoint обратно совместимы.
4. После чтения порции подтвердить устойчивость её страниц повторным сравнением
   полных сигнатур и терминальности последней страницы. Это правило касается
   и legacy-resume: после новых страниц повторно проверить исходный anchor
   сохранённого префикса. Изменение состава после первичной проверки должно
   оставлять порцию незавершённой. Поддиапазоны покрывают [L,U] непрерывно.
   Сохранить прежний max_pages для страниц данных; проверки ограничены числом
   прочитанных страниц плюс двумя boundary-probe и учитываются отдельно, не
   маскируются в статистике. Диапазон в одну секунду, не
   помещающийся в бюджет/не стабилизирующийся, даёт явный blocked, не потерю.
5. Верхняя граница всего endpoint остаётся замороженной до завершения всех
   поддиапазонов. Более поздние изменения забирает следующий штатный цикл.
   Версии одного ID с разным updated_at сохраняют новейшую доказанную версию;
   конфликт одного ID с одинаковым updated_at не угадывать. Не продвигать
   курсоры/freshness и не применять неполный общий набор четырёх endpoint.
6. Диагностика без ПДн: реальные запросы/страницы/перенесённые записи/сохранённые
   диапазоны/reset reason/время. Не добавлять потоковый журнал каждой записи.

## B. Wappi

1. После исчерпанного повтора одного нестабильного чата продолжать независимо
   проверяемые чаты в пределах прежнего бюджета. Не принимать плохие сообщения,
   не обновлять их маркеры и не считать full_audit/профиль завершёнными.
2. Использовать существующее частичное сохранение проверенных сообщений и
   checkpoint при изолированном full-history drift и доказанном каталоге.
   Неполнота каталога, дрейф provenance и недоказанное исчезновение истории
   не получают такого разрешения. Транзакция сообщений и checkpoint связаны.
3. Отказы снятия карантина сохраняют исходные записи/владельцев побайтно.
   Новое pending сообщение должно сохраняться как event+conflict, без chunks,
   а не превращаться в один conflict через preserve_existing_event.
4. Сохранять точный исходный page.reason/фазу/offset/число дублей/сравнение
   сигнатур в существующей диагностике, не клиентский текст. Корневое
   исправление нестабильного чата выбирать только по ограниченному live-probe;
   не вводить нормализацию/исключение сообщения по предположению.
5. Probe штатного helper (limit100, бюджет4) воспроизвёл фактический триггер:
   страницы0/100/200 содержат100/100/3сырых сообщения; в последней2уникальных,
   из них одинID уже был на прежней странице. Нормализация валидна, но ранний
   seen_message_ids.intersection завершает чтение до проверки сигнатур.
   Разрешить схлопывание только одного и того же messageID с идентичной
   смысловой подписью внутри одного profile/chat, затем оставить обязательную
   проверку каждой прочитанной страницы. Разное содержимое одногоID, смена
   порядка/подписи на проверке, нетерминальная повторяющаяся страница без
   новыхID остаются drift. Offset считает сырые строки, а не число уникальных.
   Нормализатор и трактовку timestamp не менять без нового доказательства.

## СТОП

Неподтверждённое право writer, занятый lock, изменение чужих файлов/защищённых
входов, необходимость внешней записи или клиентской отправки — остановка
операции. Ошибка границы/пагинации/происхождения не переводится в успешность.
До кода обязателен canonical preflight. Не менять работающий процесс и не
включать расписание до двух принятых циклов. Кодовый бюджет: до150строк нового
механизма, проверки безопасности и тесты не сокращать ради бюджета; превышение
обычного кода сначала обосновать сравнением двух минимальных вариантов.

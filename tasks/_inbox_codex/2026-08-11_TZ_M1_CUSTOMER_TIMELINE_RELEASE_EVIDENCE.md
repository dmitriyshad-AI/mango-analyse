# M1: закончить Customer Timeline на одном SHA и доказать пользу менеджеру

## 0. Простое объяснение для Дмитрия

M1 сделал полезную работу, но первый отчёт завысил готовность:

- `9/10` полезных черновиков независимо не подтвердилось: два прогона дают примерно `7-8/10`;
- `59/59 manager-ready` проверяло в основном наличие текста, а не свежесть и смысл действия;
- `824 фрагмента` суммировались по повторным вызовам и не означают `824` уникальных события;
- база построена кодом `9700fa0d`, а финальный код имеет SHA `c32f8da5`;
- ветка смешала ядро Timeline, живой путь черновика и служебные изменения.

Главный Codex принял отдельно только маленький фикс красной линии: если переданы
AMO lead и contact, обе связи обязаны точно указывать на одного клиента. Не
реализовывать это повторно.

Эта задача должна собрать чистое ядро Timeline от нового `main`, устранить два
архитектурных раздвоения, пересобрать данные тем же кодом и показать фактический
результат менеджера на 10, затем на 100 клиентах.

## 0.1. Образ результата

После задачи существует одна чистая ветка-кандидат, в которой:

1. У Customer Timeline один владелец формирования bot-context и один владелец
   исправления связей событий.
2. Точная версия кода дважды обрабатывает один и тот же набор данных без новых
   бизнес-строк, дублей и смены владельца события.
3. Для каждого клиента доказано, откуда взяты имя, ребёнок, семья, телефоны,
   почта, сделки, оплаты, посещения, письма, Wappi и звонки.
4. Менеджер видит полный фактический профиль и понятный следующий шаг либо
   понятную причину бездействия.
5. Один клиент никогда не получает историю другого, включая братьев/сестёр с
   общим телефоном.
6. Никаких записей в AMO, Tallanto, Wappi или рабочую Timeline. Публикация и
   live-включение остаются отдельным решением Дмитрия.

## 2. Собрать чистое ядро, а не слить 26 коммитов

Не merge и не cherry-pick всей ветки `c32f8da5`.

### 2.1. Один владелец bot-context

В доноре найден прямой канал `customer_timeline_amo_lifecycle`, который читает
`customer_opportunities` и добавляет данные в prompt параллельно с сохранёнными
`bot_context_chunks`/Stage4b. В текущем `main` этого кода нет.

Нужно:

1. Нарисовать фактический путь `source -> event -> managed context -> prompt`.
2. Прямой SQL-канал lifecycle из донора не переносить.
3. Не создавать вместо него новый managed channel/framework в этой задаче. Если
   lifecycle-факта не хватает в текущем `main`, зафиксировать отдельную находку с
   числом затронутых карточек и не расширять scope.
4. Не держать параллельно persisted и прямой SQL-каналы одного бизнес-факта.
5. NEG: удалить/сменить lifecycle-событие в источнике; старое значение должно
   исчезнуть из prompt, а не остаться в обходном канале.

### 2.2. Один владелец исправления identity

В доноре основной путь `_upsert_event` соседствует с регулярным post-factum
`reconcile_superseded_event_dependencies()` и
`repair_hash_valid_event_identity_cache()` в Stage4b. В текущем `main` этих
repair-функций нет.

Нужно:

1. Исправлять владельца в канонической точке ingest/upsert.
2. Post-factum repair из донора не переносить. Если старая база действительно
   требует миграции, описать отдельную находку и число строк; реализация миграции
   не входит в эту задачу.
3. Доказать перенос оплаты/письма/Wappi-события от A к B:
   после повтора событие есть только у B, старый context A retired, счёт строк
   закрыт.

### 2.3. Не смешивать живой бот с ядром Timeline

Из текущего блока исключить изменения `src/mango_mvp/channels/**`, ADR-003,
regex snapshots и P0-тесты. Драфтовые коммиты `be2654b1...c32f8da5` оформить
отдельным patch/веткой после отдельной смысловой приёмки.

Особенно запрещено ослаблять P0-проверку до произвольного набора finding codes.
Допустимое множество должно быть перечислено явно.

## 3. Красная линия: чужие данные

1. Фикс полной пары `AMO lead + contact` уже в `main`; не дублировать.
2. Проверить не только `chunk.customer_id`, но и происхождение семейной/детской
   связи внутри одного customer ID.
3. В обязательную выборку включить:
   - двух детей с общим телефоном;
   - одинаковые/похожие имена;
   - ручную identity-связь;
   - старую и новую AMO-сделку;
   - событие, которое ранее переезжало между клиентами.
4. Общий телефон сам по себе означает возможную семью, а не конфликт и не
   разрешение показать данные одного ребёнка в контексте другого.
5. Истину по ученику/родителю/телефону брать из сохранённого Tallanto-сырья;
   не обращаться повторно к API без доказанной необходимости.
6. Canary-мутация владельца обязана сделать тест красным.

## 4. Сборка данных на том же SHA

### 4.1. Честно назвать режим

На M1 не было полного frozen raw set. Поэтому запрещено называть работу холодной
пересборкой, если использована копия текущей staging-базы.

На основном Mac уже есть свежая staging и сохранённые инкрементальные источники:

- `~/.mango_local/customer_timeline_nightly/.codex_local/staging/nightly_dv2_sources/`;
- актуальная `customer_timeline_staging.sqlite` внутри этого staging-контура.

Не скачивать неизменённую историю повторно. Для M1 запросить у главного Codex
копию только нужных snapshots/cursors и staging SQLite по проводу либо через
контрольный пакет с SHA-256. Секреты в Git и audit pack не включать.

Допустимы два отдельных режима:

- `cold_rebuild` — только если передан полный зафиксированный набор сырья;
- `incremental_convergence` — копия свежей staging + сохранённые snapshots/cursors
  + только новые/изменённые записи.

Оба режима полезны, но в отчёте не подменяют друг друга. Для
`incremental_convergence` отдельно записать `input_generation_sha`, SHA каждого
изменяющего прохода и `final_candidate_sha`; исторические строки не обязаны быть
созданы одним SHA. Строгое равенство builder SHA и candidate SHA требуется только
для настоящего `cold_rebuild`. Пока полный raw set не передан, `cold_rebuild`
помечается `NOT_RUN`.

### 4.2. Два неизменных прохода

На точном финальном SHA и фиксированных `as_of`, snapshots и cutoff выполнить два
последовательных прохода. На втором: fingerprint бизнес-таблиц не меняется,
`created=0`, `updated=0`. Разрешённый рост только у заранее перечисленных
run/audit/cursor rows; их diff показать отдельно.

Для каждого источника сопоставить уже существующие поля его отчёта с:

- fetched/new/changed/reused/skipped/quarantined;
- время чтения, обработки и записи;
- закрытый баланс `total = linked + quarantine + expected_excluded + error`;
- fingerprints бизнес-таблиц до и после;
- рост только явно разрешённых run/audit rows.

Не добавлять общий счётчик или новый контракт в продуктовые импортёры только ради
этого отчёта; mapping выполняется в audit-only оснастке.

NEG баланса: убрать одну корзину из копии отчёта/измерителя — gate обязан стать
красным. Изменять продуктовую базу для NEG запрещено.

Обязательные источники: AMO deals, Tallanto cards/payments/attendance, Wappi
Telegram/MAX, mail, identity, family graph, managed bot-context. Calls здесь
только читаются из уже импортированных `mango_processed_summary` и закреплённого
D2 ready manifest с producer SHA: fetch, ASR и Calls Process A/B не запускать.
В manager dossier звонки видимы; в bot-context они остаются запрещённым источником
по текущей source policy.

Ожидаемо непривязанные attendance-события по D-114 остаются retry-очередью и не
блокируют freshness, если fetch завершён и баланс закрыт. Не чинить D-114 заново.

## 5. S10: фактический путь контекста

На финальном SHA дважды выполнить один и тот же набор 10 клиентов:

`exact AMO pair -> Timeline managed context -> build_draft -> перехваченная AMO note`

Никаких внешних записей.

Обязательные отрицательные контроли:

1. Подменить exact lookup на другого клиента: исходный context не должен прийти.
2. Вернуть `None`: offline-ID не должен незаметно стать live AMO route.
3. Monkeypatch-ом убрать один источник: он исчезает из context и provenance.
4. Перехватить AMO POST/PUT/PATCH: счётчик внешних записей остаётся `0`.

Для каждого сохранить обезличенно:

- полный входной вопрос;
- источники и provenance;
- фактический context модели;
- фактический текст черновика;
- route и причина;
- следующий шаг/причина бездействия.

Обязательные Timeline-сценарии:

1. семейный телефон;
2. оплата и активная сделка;
3. письмо и Wappi одного клиента;
4. ручная identity-связь;
5. событие, ранее перемещавшееся между клиентами.

Критерии каждого из двух прогонов:

- `10/10` точная пара AMO;
- `0` чужих фактов, включая sibling leak;
- `10/10` context соответствует первичным событиям и provenance;
- `0` внешних записей.

Фактические draft-тексты сохранить как отдельное наблюдение, но не менять
`src/mango_mvp/channels/**` и не блокировать Timeline core качеством QR,
документов или благодарности. Если полезность ниже 80%, оформить отдельный bot
patch/TЗ. Новый regex/keyword-словарь запрещён. Использовать существующий dry-run,
новый перехватчик не строить.

## 6. S100: проверить продукт, а не заполненность полей

Сформировать 100 фактических manager dossier по замороженному списку хешированных
customer IDs из текущего пакета. Для каждого поля явно хранить состояние
`known/absent/conflict/not_applicable`; «полная карточка» означает объяснённое
состояние, а не обязательное наличие имени, ребёнка или действия. Отдельно
показать страты exact/family/review/empty/closed и source denominator.

Фактические LLM-черновики
сгенерировать для стратифицированной выборки 30 клиентов пропорционально
`active/review`; отдельно указать размер выборки и 95% доверительный интервал.
Наличие summary/chunk не равно полезному ответу.

Для карточки показать:

- имя/семью/бренд;
- деньги, активные сделки, посещения;
- ключевую хронологию и возражения;
- следующий шаг либо код причины бездействия;
- владельца, действие, срок и provenance.

Правила категорий:

- `active`: действие конкретно, источник свежий, срок нормализован и не прошёл;
- `review`: причина, владелец, конкретное действие и будущий срок;
- `closed`: сохранена точная пара `обязательство -> закрывающее событие`;
- `empty`: указано, почему шага нет, и источник обогащения либо честное исключение.

Запрещено считать active готовым только по непустому тексту. Шаг из декабря 2025
или «через час/завтра» из прошлого не является активным.

Критерии:

- долю полезных 30 черновиков показать с 95% доверительным интервалом; это
  отдельный bot-semantic verdict, а не блокер Timeline core;
- минимум 80% бизнес-знаменателя `active + review` manager-ready;
- `closed` и `empty` показываются отдельно и не улучшают процент;
- `0` чужих фактов, выдуманных действий и скрытых потерь.

Нулевые показатели подтверждать provenance-сверкой и canary-мутациями, а не
голосованием моделей. Расхождение модели и сырья разрешает главный Codex по
первичным данным.

## 7. Починить измерители

1. Не складывать один и тот же context дважды. Показывать отдельно:
   `calls`, `returned_items`, `unique_chunk_ids`, `unique_event_ids` и
   `same_text_different_events`.
2. `duplicate_items=0` внутри одной выдачи не выдавать за уникальность всей S100.
3. `10/10 exact AMO` на заранее exact-eligible пуле подписывать как позитивный
   путь, не как точность resolver по всей базе.
4. Сравнить полный набор collected pytest node IDs. Каждый исчезнувший base-тест
   либо восстановить, либо объяснить эквивалентной заменой.
5. `formal`, `data`, `semantic`, `business`, `runtime` — пять отдельных вердиктов.
6. NEG счётчика: подать один chunk дважды — `returned_items` растёт, а
   `unique_chunk_ids` не меняется.

## 8. Уборка

До финала получить неблокирующий cleanup-report от GPT/Claude уборщиков.

Уже доказанные кандидаты:

1. не переносить из донора дублирующий `_parse_aware_timestamp`; если полезная

2. не переносить из донора прокладку `normalize_as_of_utc`; использовать alias

3. не переносить M1 worktree/task bookkeeping;
4. не переносить unrelated `6f82afb4` в Timeline-коммит.

Для каждого нового удаления: Graphify -> исходники -> живой entrypoint -> тест
отсутствия вызова. Production LOC финального ядра не должен расти относительно
полезной Timeline-части `c32f8da5`; рост требует отдельного объяснения.

## Приёмка

1. Полный pytest base/candidate на одной версии Python: новых падающих node IDs `0`.
2. Точечные тесты identity, family, money, attendance, Wappi, mail, bot-context,
   next-step и manager dossier.
3. SQLite `quick_check=ok`, FK violations `0`.
4. Два data-прохода с нулевым diff бизнес-таблиц и `created/updated=0` на втором.
5. Два S10-прогона с одинаковым provenance/context balance; текст модели может

6. S100 со 100 карточками и 30 стратифицированными текстами.
7. Breaker-мутации красной линии, retirement, дублей, stale next-step и
   obligation closure.
8. ПДн не попадают в публичный audit pack.

## СТОП

Остановиться и не публиковать, если:

- для incremental-режима не записаны input/pass/final SHA; для cold rebuild
  builder SHA отличается от candidate SHA;
- режим сборки назван холодным без полного сырья;
- без отдельного подтверждения требуется внешнее AMO/Tallanto/Wappi/mail чтение;
- любой закрытый баланс не сходится;
- обнаружены чужие данные;
- S100 не содержит 100 карточек и 30 стратифицированных фактических текстов;
- второй проход создаёт новые бизнес-строки;
- Timeline core снова смешан с live/draft/publish-контуром.

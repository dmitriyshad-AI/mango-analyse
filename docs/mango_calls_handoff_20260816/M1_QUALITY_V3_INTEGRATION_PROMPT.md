Дата: 2026-08-17.

## Что нужно сделать

Интегрировать ветку `codex/mango-calls-quality-v3-m4-20260816` в отдельном
чистом worktree M1, проверить её на локальных данных и доказать качество на
лестнице `1 -> повтор 1 -> 10 -> калибровка 50 -> 50+50 -> 200`. Не сливать в `main`, не менять
живую службу, Google-таблицу, AMO, Tallanto и Customer Timeline до отдельного
разрешения Дмитрия.

Точный SHA ветки Дмитрий передаст вместе с этим файлом. Не использовать просто
«последний коммит»: после `fetch` выполнить `git rev-parse HEAD` и сравнить с
переданным SHA побайтно.

## Зачем нужна эта версия

1. Analyse читает единый разговор в порядке реплик, а не два монолита дорожек.
2. Названия `Менеджер` и `Клиент` разрешены только тогда, когда исходный ответ
   Mango для этой записи подтверждает стороны и совпадает с сохранёнными
   физическими дорожками.
3. Если доказательства нет или оно неоднозначно, разговор сохраняется целиком
   как `Спикер A/B`, коммерческие выводы не публикуются и вызов модели не
   выполняется.
4. Оплата, отказ, возражение, следующий шаг и срок принимаются только со ссылкой
   на существующую реплику этого же звонка.
5. Повтор неизменного Analyse использует существующий кэш. Ключ включает все
   параметры, влияющие на ответ. Точные токены записываются только из полного
   ответа провайдера; выдуманные оценки запрещены.
6. Google-публикация остаётся одним детерминированным скриптом и не вызывает
   Codex. Включать её можно только после отдельной приёмки Дмитрия.

## Получение ветки

```bash
cd <M1_REPOSITORY>
git fetch origin codex/mango-calls-quality-v3-m4-20260816
git worktree add ../Mango_calls_quality_v3_m1 \
  -b codex/mango-calls-quality-v3-m1-integration \
  origin/codex/mango-calls-quality-v3-m4-20260816
cd ../Mango_calls_quality_v3_m1
git status --short --branch
git rev-parse HEAD
```

Рабочее дерево должно быть чистым, а SHA должен совпасть с SHA из сообщения
Дмитрия. При несовпадении остановиться. Не использовать чужой worktree и не
переносить в него незакоммиченные файлы.

## Обязательная доработка capture на M1

Статический код этой ветки умеет строго разобрать официальный ответ
`/vpbx/queries/recording_transcripts`, проверить его хэш и связать с одним
`source_call_id`. Но существующий producer ещё не доказал сохранение этого
ответа в поле `transcript_variants_json.provider_role_evidence`.

До любого реального чтения Mango API, запуска ASR или Resolve/Analyse M1 обязан
остановиться и получить отдельное явное разрешение Дмитрия. Сначала выполняются
только локальные тесты и предварительный просмотр на уже переданных фикстурах.

Первоисточник схемы:
`https://docs.mango-office.ru/ru/5_api-i-razrabotka/1_api-mango-office/5_opisanie_metodov_api_virtualnoy_ats_mango/5_5_api_zapisi_razgovorov_rechevaya_analitika/3_5_5_poluchenie_spiska_rasshifrovok.html`.
Официальный PDF Mango (редакция 07.2026, страница 93) задаёт необычный формат
запроса: значение `recording_id` внутри подписываемого JSON является **строкой,
в которой сериализован массив**. Для одного ID это буквально
`{"recording_id":"[\"ID\"]"}`, а не `{"recording_id":["ID"]}`.
Публичный пример ответа использует объект одной записи в `data` и пары
`[role, text]`; пакетный ответ может содержать список записей. Код принимает
только эти явные формы и эквивалентные пары с ключами `role/text`. Фактическое
сырое тело первого ответа обязательно приложить к локальной проверке. Если
форма отличается, остановиться и расширить parser отдельным тестом, а не
угадывать данные.

До пилота M1 должен минимально встроить в существующий capture:

1. Получать transcript Mango пакетами не более 500 `recording_id` через
   `MangoOfficeClient.fetch_recording_transcripts()`. Для каждой записи отдельно
   вызывать `parse_recording_transcripts_response()`; сетевой ответ сам по себе
   ещё не является доказательством ролей.
2. Полное исходное тело пакетного ответа сохранить **один раз** в owner-only
   capture-хранилище по SHA-256: атомарно в `<capture_root>/<sha256>.json`,
   каталог `0700`, файл `0600`, без симлинков, ACL и облачной синхронизации.
   Перед любым изменением БД заново прочитать файл, сверить его SHA-256 и наличие
   запрошенного `recording_id`. Ошибка записи/чтения/хэша/ID означает карантин и
   0 изменений БД. В строку звонка не копировать общий пакет с
   чужими разговорами. В per-call evidence хранить только канонический конверт
   конкретного `recording_id`, SHA списка фраз и ссылочный
   `batch_response_sha256`.
   Пакет хранить вне Git до письменной приёмки пилота; удаление разрешено только
   отдельным решением Дмитрия. Отсутствие файла до приёмки означает STOP.
3. Проверить `recording_id` по неизменяемым метаданным исходной записи из
   capture-слоя. Само поле из provider evidence не является доказательством.
   Связать в одной записи `source_call_id`, `recording_id`, время звонка и SHA
   исходного capture-конверта; несовпадение любого элемента отправляет звонок в
   карантин. Проверенный capture-слоем `recording_id` хранится независимо в
   столбце `call_records.source_recording_id`; класть его внутрь изменяемого
   `transcript_variants_json` вместо этого столбца запрещено.
4. Не доверять отдельным копиям `channels`, порядку каналов, имени файла,
   приветствию, направлению звонка или догадке модели.
5. Если API не возвращает пригодные `client/operator` фразы либо они не
   совпадают с дорожками, сохранить разговор как `Спикер A/B` и остановить
   публикацию коммерческих выводов.
6. Не считать внутренний звонок менеджер-клиентом: два имени сотрудников или
   метки `Канал 1/Канал 2` не подтверждают внешнего клиента. Допустим только
   явный `Клиент` либо телефон на клиентской стороне.
7. Записывать evidence условным обновлением: только если `id`, `source_call_id`,
   `source_recording_id` и прежний `transcript_variants_json` всё ещё совпадают
   с прочитанным снимком. При первом новом evidence перевести только производные
   статусы Resolve/Analyse/sync этого звонка в `pending`; raw audio, Whisper,
   GigaAM и прежние результаты не удалять. `rowcount != 1` означает гонку и
   карантин, а не повторную безусловную запись. Повтор с тем же evidence SHA
   обязан быть пустым: 0 обновлений, 0 Resolve, 0 Analyse, 0 токенов.
8. Сохранить агрегированный технический отчёт без текста и телефонов: получено,
   связано, quarantined, неизменённо переиспользовано, повторно обработано,
   cache hit, вызовы модели и точные токены. Несходящийся баланс блокирует
   следующую ступень.

### Точная интеграция в рабочую БД M1

1. До изменения копии БД выполнить read-only инвентаризацию. Если столбца нет,
   штатная миграция `init_db()` должна добавить
   `source_recording_id VARCHAR(256)` и индекс
   `ix_call_records_source_recording_id`; ручное редактирование production-БД
   запрещено. До пилота выполнить read-only поиск повторяющихся непустых
   `source_recording_id`; любой дубль означает STOP до разбора связи.
2. `prepare_ingest_inputs()` пишет в `metadata.csv` `recording_id` только когда
   вызов `entry_recording_ids(entry)` для **конкретного `ManifestEntry`** после
   удаления пробелов и дублей возвращает ровно один непустой ID. Если
   `canonical_recording_id` задан после разрешения дубля, этот единственный ID
   обязан с ним совпадать; для обычной записи пустой `canonical_recording_id`
   не отменяет найденный единственный ID. Весь manifest может и должен содержать
   много записей. `ingest_from_directory()` переносит очищенное значение в
   `CallRecord.source_recording_id`.
3. Для старой строки backfill разрешён только из того же сохранённого capture
   manifest при однозначной связи. Имя файла, порядок каналов и содержимое
   разговора доказательством не являются.
4. Capture adapter объединяет новый per-call evidence с существующим JSON, не
   заменяя ASR-варианты. Условный `UPDATE` сравнивает весь прежний JSON и три
   идентификатора из пункта 7. Тест обязан имитировать конкурентное изменение и
   получить 0 записанных строк.
5. Rescue-ASR не имеет права заменить provider evidence: после rescue остаётся
   исходный per-call конверт и исходный `batch_response_sha256`.

Нельзя ослаблять пороги соответствия на одном примере. До объявления ролей
доверенными собрать калибровочную выборку минимум из 50 вручную проверенных
разговоров разных типов, сохранить обезличенные числовые показатели и матрицу
ошибок. Пороги меняются только отдельным решением Дмитрия по этому отчёту.

До любой плановой внешней записи M1 также обязан подключить приёмник ошибок и
доказать контролируемым сбоем, что ненулевой код выхода дошёл до назначенного
ответственного. Репозиторный launchd-шаблон намеренно работает без `--execute`.

Новый контракт меняет версии промпта и ключ кэша. Старый кэш не удалять, но
первый Analyse нового доверенного звонка будет холодным и вызовет модель.
Массовый повтор исторических звонков запрещён до отчёта по 50 звонкам: число
новых вызовов, точные токены провайдера и согласованный Дмитрием бюджет.

До bootstrap Google выполнить только чтение заголовка. Текущий контракт содержит
17 столбцов и добавляет столбец `Основание ключевых выводов` перед
`Что проверить РОПу`. Если живой лист имеет прежние точные 16 столбцов,
остановиться и подготовить отдельный план миграции: вставить новый столбец O,
проверить формулы/ширины/readback и получить явное разрешение владельца. Код не
меняет заголовок живого листа автоматически.

## Лестница реальной проверки

Каждая ступень запускается только после зелёного отчёта предыдущей и отдельного
разрешения Дмитрия на реальное чтение/обработку. До него запрещены Mango API,
ASR, Resolve/Analyse и внешние записи: допустимы только локальные тестовые
фикстуры, локальный отчёт и локальный предварительный просмотр.

### 1. Один звонок

- Выбрать обычный двухсторонний звонок с раздельными дорожками.
- Получить и сохранить provider evidence Mango.
- Прогнать только этот звонок через штатные стадии.
- Вручную сравнить аудио, порядок реплик и роли.
- Проверить, что ни одна реплика не исчезла, не переставилась и не приписана
  другой стороне.
- Проверить доказательства для результата, оплаты, возражения и следующего шага.

### 2. Тот же звонок повторно

- Повтор не должен заново скачивать неизменённое, создавать дубль или вызывать
  модель.
- На уровне службы ожидаются фактические поля отчёта:
  `status=idle`, `stop_reason=unchanged_snapshot`, `new=0`, `reused=1`,
  `process_a.counters.drop.reused=true`, `process_b.status=idle`, а также
  `process_a.safety.runs_resolve_analyze=false`. Последнее доказывает 0 Resolve,
  0 Analyse и отсутствие модельного вызова. Готовая строка переиспользуется без
  входа в Analyse; не требовать отсутствующий в service-report
  `model_call_count`.
- Отдельный прямой тест Analyse на том же входе доказывает
  `analysis_meta.cache_hit=true` и отсутствие второго вызова модели. Не требовать
  `cache_hit=true` от штатного service-repeat, который Analyse вообще не вызвал.
- Баланс входов, результатов, карантина и ошибок обязан сходиться.

### 3. Десять звонков

Включить обычный диалог, входящий/исходящий, один голос, автоответчик, шум,
перебивания, длинную запись, неоднозначные дорожки, оплату и явное отрицание
оплаты. Сверить каждый звонок вручную.

### 4. Калибровка на 50 вручную проверенных звонках

- До чтения результата заморозить список ID, правила отбора и исключения.
- Сопоставить исходный ответ Mango, физические дорожки, аудио и итоговые роли.
- Посчитать ошибки по каждому типу звонка; не менять пороги по одному примеру.
- Приложить точные расходы модели и долю звонков, на которых модель не вызывалась.
- Только Дмитрий по этому отчёту принимает или отклоняет пороги ролей.

### 5. Сто звонков: 50 доверенных + 50 недоверенных

- Эти 100 звонков не пересекаются с 50 звонками калибровки; список ID и правила
  отбора/исключения замораживаются до чтения результата.
- У доверенных проверить точность ролей и ссылок на реплики.
- У недоверенных проверить сохранность полного текста, `Спикер A/B`, отсутствие
  ФИО, оплаты, обещаний, следующих шагов и иных выводов от имени стороны.
- Подтвердить, что недоверенные звонки не тратят токены модели.

### 6. Двести звонков

Стратифицировать по менеджерам, длительности, направлению, качеству аудио и
типам разговора. Сформировать отчёт для РОПа и отдельный отчёт о технических
ошибках без телефонов и текста разговоров.

## Численные критерии пилота

Знаменатель всегда указывать явно: сколько строк проверено и сколько исключено
по технической причине.

- Доверенные роли: 100% проверенных звонков имеют правильные стороны и порядок
  реплик; одна ошибка останавливает следующую ступень.
- Недоверенные роли: 100% строк имеют `Спикер A/B`, 0 коммерческих выводов от
  имени клиента/менеджера и 0 вызовов модели.
- Результат, возражение, следующий шаг и срок оцениваются **по отдельности**:
  для каждого поля считать TP/FP/FN/NA, precision и recall должны быть не ниже
  95%. Если применимых примеров поля меньше 20, вердикт по нему `NOT_PROVEN`, а
  общий процент не имеет права скрыть провал одного поля. Ссылки на реплики и
  утверждения об оплате должны быть правильны в 100% применимых случаев.
- Управленческий конспект: минимум для 48 из 50 trusted-звонков один заранее
  назначенный РОП за 30 секунд без полной расшифровки правильно отвечает на два
  фиксированных вопроса: «чем закончился разговор?» и «какой следующий шаг?».
  Правильные ответы фиксируются до начала проверки.
- Логи, инциденты и закрытый баланс: 100% без телефонов, почты и текста
  разговора.
- Любое противоречие оплате, явному отказу либо устаревшая внешняя запись —
  немедленный STOP независимо от общей доли успеха.

## Контроль токенов

Для каждой ступени приложить агрегаты:

- сколько звонков не вызвали модель из-за неподтверждённых ролей;
- сколько не вызвали модель как детерминированно несодержательные;
- сколько попали в кэш;
- сколько реально вызвали модель;
- для каждого сочетания `provider/model/prompt_version` закрытый баланс вызовов:
  `exact_usage_model_calls + partial_usage_model_calls +
  unavailable_usage_model_calls = model_calls`; итог обязан иметь
  `model_usage_balanced=true` и `identity_balanced=true`;
- `prompt_tokens`, `completion_tokens`, `total_tokens` только там, где это поле
  вернул провайдер; неполный ответ относится к `provider_partial`;
- сколько вызовов имеют `usage=unavailable`; кэш и детерминированные пропуски не
  считаются вызовами модели.
- журнал `analysis_attempts_json` содержит уникальные `attempt_id`; состояния
  `reserved` и `indeterminate`, повтор ID или повреждённый JSON означают STOP;
- ответ модели появляется в кэше только после подтверждённого
  `analysis_status=done`; потерянный commit-ack проверяется обратным чтением и
  не создаёт вторую попытку;
- одна запись `attempt_id` соответствует ровно одному внешнему вызову. Внутри
  одного Analyse нет скрытых повторов Codex: техническая ошибка фиксируется и
  возвращается в управляемую очередь;
- для Ollama изменение адреса сервиса, `think`, `temperature` или `num_predict`
  меняет и ключ кэша, и `analysis_source_sha256`;
- cost gate должен пройти до первого и каждого компенсационного Google-запроса.

Запрещено оценивать токены по символам. Resolve работает с
`RESOLVE_LLM_PROVIDER=off` во всех режимах, включая controlled-профиль:
физические дорожки Mango уже являются источником ролей, поэтому модель здесь
только дублирует Analyze. Publisher не использует LLM. Неизменённые
звонки должны переиспользовать сохранённые ASR/Resolve/Analyse результаты.

До измерения на замороженной выборке нельзя снижать модель или глубину Analyse
ради экономии. Экономия в этом выпуске достигается только доказуемым исключением
лишней работы: неподтверждённые роли и детерминированно несодержательные звонки
не вызывают модель, повтор использует сохранённый результат/кэш, compact-проход
расширяется до full только по явным признакам недостаточности, а публикация не
вызывает Codex вообще. Перед ступенью 50 Дмитрий задаёт допустимый бюджет; при
несходящемся балансе попыток или неизвестном фактическом расходе следующая
ступень остаётся `STOP`.

## Жёсткие условия остановки

Остановиться и ничего не публиковать, если:

- пропала или переставилась хотя бы одна реплика;
- `Менеджер/Клиент` появились без связанного с этим звонком ответа Mango;
- provider evidence можно перепривязать к другому `recording_id` или
  `source_call_id`;
- два звонка имеют один непустой `source_recording_id`;
- рискованный вывод не имеет точной ссылки на реплику;
- недоверенный звонок получил коммерческий вывод или вызвал модель;
- повтор вызвал модель или создал дубль;
- закрытый баланс не сходится;
- журнал попыток модели содержит незавершённую, неопределённую или повторную
  попытку;
- найден второй Google-writer или одновременно активны два владельца службы;
- лог/инцидент содержит телефон, почту или текст разговора.

## Что вернуть владельцу проекта

1. Ветку и точный SHA интеграции M1.
2. Список минимальных изменений capture и изменённых файлов.
3. Команды и полные итоги тестов.
4. Отчёты ступеней с закрытым балансом и расходом токенов.

   сверку аудио.
6. Отдельные вердикты `formal`, `semantic`, `business`, `data`, `runtime`.
7. Явный список того, что не доказано.
8. Решение `GO/STOP` отдельно для следующей ступени, Google и AMO.

ступени. Google, AMO, Tallanto, Customer Timeline, launchd-cutover и массовый
production-запуск остаются `STOP`.

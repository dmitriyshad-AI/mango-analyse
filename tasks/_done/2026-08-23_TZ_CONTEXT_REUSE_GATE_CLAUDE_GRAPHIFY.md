## 0. Зачем это нужно

В проекте повторяется один и тот же дорогой цикл:

1. задача частично реализуется;
2. попытка переносится в `_done`, хотя исходная проблема не закрыта;
3. через несколько недель новый диалог не видит старую реализацию;
4. похожий механизм строится второй раз с немного другим поведением;
5. обе версии остаются в коде, тестах, ветках или незакоммиченном дереве;
6. следующий аудит снова начинает поиск почти с нуля.

Цель этого ТЗ: перед добавлением функции, класса, флага, пайплайна или
значимой ветки поведения агент обязан доказать одно из четырёх решений:

- `reuse` — готовое уже есть, используем его;
- `extend` — владелец механизма есть, расширяем его;
- `port` — ценная реализация есть только в другой ветке, переносим её;
- `new` — после воспроизводимой проверки аналога нет, строим новое.

Если доказательства недостаточны, решение только `stop`, а не новый код.

Graphify используется первым, но только как навигатор. Решение всегда
подтверждается исходником, Git, тестом или runtime-фактом.

## 3. Новый контракт ТЗ

Для новых ТЗ, меняющих `src/` или создающих значимый механизм в `scripts/`,
добавить поля:

```text
Feature-ID: стабильный.идентификатор
Problem-ID: стабильный.идентификатор.проблемы
Изменение: new|extend|fix|remove
Ключевые-символы: symbol_a,symbol_b
Ключевые-слова: фраза 1,фраза 2
```

Правила:

- `Feature-ID` описывает способность системы, а не конкретную попытку;
- `Problem-ID` одинаков для всех повторных попыток закрыть одну проблему;
- старые ТЗ массово не мигрировать;
- требование действует для новых ТЗ после принятия этого изменения;
- документация без кода может использовать `Изменение: none`;
- отсутствие полей в новой кодовой задаче является ошибкой `tz_lint`.

## 4. Шаг A: усилить inventory_before_build

### A1. Порядок поиска

Порядок обязателен и отражается в отчёте:

1. Graphify `stats`: зафиксировать ревизию карты и текущий `HEAD`. Не писать
   второй reader: переиспользовать `load_output_manifest()` и `stale_banner()`
   из `src/mango_mvp/graphify_structural.py`; ревизию брать из
   `mango_structural_manifest.json`, а не из `graph.json`.
2. Точечные Graphify-запросы по каждому символу и бизнес-возможности.
3. Все worktree из `git worktree list --porcelain`: tracked, modified, staged
   и untracked-код. Переиспользовать `parse_worktrees_porcelain()` из
   `scripts/preflight.py`; работать только read-only, без checkout/switch.
4. Сырой поиск `rg` по символам, строкам, тестам, флагам и вызывающим.
5. Git refs: невлитые локальные и remote-ветки, теги, история `-S/-G`.
6. `tasks/`: running, done, failed и inbox по `Feature-ID`, `Problem-ID`,
   символам и синонимам.
7. свежие `audits/_inbox/` и `docs/DECISIONS_LOG.md`.
8. подтверждение кандидата чтением исходника или `git show <sha>:<path>`.

Graphify не имеет права доказывать отсутствие. Если карта устарела, можно
использовать найденный по ней кандидат, подтверждённый в сырье, но нельзя
выдавать `ABSENT`.

Поиск в других worktree ограничить кодовыми зонами `src/`, `scripts/`,
`tests/`, `.claude/` и tracked-документами задачи. Не читать `product_data/`,
`stable_runtime/`, `.mango_local`, почту, аудио, звонки и клиентские выгрузки.

В `audits/_inbox/` читать только имя каталога, `manifest.json`,
`changed_files.txt`, `implementation_notes.md`, `risk_review.md` и
`backward_compatibility.md`. Raw/test outputs без явного whitelist не читать.

Исправлять причины шумного результата, а не симптом:

- не склеивать все термины в один Graphify-запрос;
- выполнять отдельный запрос для каждого точного символа/возможности;
- не превращать первые 1000 символов баннера Graphify в кандидата при пустом
  совпадении;
- не ставить найденный статус без подтверждения в сыром исходнике.

### A2. Классы кандидатов

Каждый кандидат получает ровно один класс:

- `ACTIVE_REUSE` — вызывается на текущем боевом/целевом пути;
- `ACTIVE_EXTEND` — текущий владелец механизма, который надо расширять;
- `PARTIAL_WORKTREE` — работа уже есть в dirty/untracked состоянии;
- `DONOR_REF` — ценная реализация существует на другой ветке или в теге;
- `IMPLEMENTED_OFF` — код готов, но выключен флагом или не подключён;
- `SUPERSEDED` — заменён более новым владельцем;
- `REMOVED_INTENTIONALLY` — удалён решением, восстанавливать нельзя;
- `FALSE_MATCH` — совпадение терминов без общей функции;
- `ABSENT_PROVEN` — после всех разрешённых проверок реализация не найдена.

### A3. Выход

Один запуск создаёт:

- `prebuild_inventory.json` — машинный отчёт;
- `prebuild_inventory.md` — короткий отчёт человеку.

Обязательные поля JSON:

```json
{
  "schema_version": "mango_prebuild_inventory_v1",
  "feature_id": "...",
  "problem_id": "...",
  "repo_head": "...",
  "branch": "...",
  "worktree": "...",
  "status_fingerprint": "sha256:...",
  "graph_revision": "...",
  "graph_matches_head": true,
  "generator_version": "...",
  "generator_command_sha256": "...",
  "queries": [],
  "coverage": {
    "graphify": "completed",
    "worktrees": "completed",
    "raw_rg": "completed",
    "git_refs": "completed",
    "tasks": "completed",
    "audits": "completed",
    "decisions": "completed"
  },
  "candidates": [],
  "decision": "reuse|extend|port|new|stop",
  "selected_owner": {"path": "...", "symbol": "...", "sha": "..."},
  "unresolved": [],
  "generated_at": "..."
}
```

Для каждого доказательства обязательны `source`, `path`, `line` или `sha`,
`why_relevant` и `verified_in_raw_source`.

Выход хранится как generated evidence внутри единственного audit pack текущей
задачи, не коммитится и не становится реестром.

### A4. Жёсткие стопы

Скрипт возвращает ненулевой код, если:

- найден `PARTIAL_WORKTREE`, но ТЗ предлагает строить новое;
- найден владелец, но нет решения `reuse/extend/port`;
- два активных владельца конфликтуют;
- Graphify устарел, а решение заявлено как `new`;
- кандидат подтверждён только названием, без исходника;
- входы слишком общие и дают шум вместо точной классификации.
- dirty-файл в заявленной зоне или с совпавшим бизнес-термином не удалось
  классифицировать: `dirty_code_unclassified`, решение `stop`.

Статус `FOUND` без класса и решения удалить.

### A5. Производительность и границы

- не вызывать `build_project_inventory()`;
- не читать БД, аудио, почту, звонки и `stable_runtime`;
- обычный запуск на текущем проекте: целевой бюджет до 10 секунд;
- сеть и внешние write-операции запрещены;
- `graphify-out` не копировать в audit pack и не передавать наружу.

Бюджет скорости проверять на этом Mac со свежей картой и фиксировать в отчёте.
Если первый корректный запуск превышает 15 секунд, остановиться и показать
профиль времени; не ускорять параллелизмом до удаления лишнего чтения.

## 5. Шаг B: сделать доказательство частью preflight

### B1. tz_lint

Для любой ТЗ, в зонах которой есть `src/` или `scripts/`, проверить поля
раздела 3. Старые code-ТЗ массово не мигрировать, но при следующем взятии в
работу они должны получить поля; отсутствие `Feature-ID` не является способом
обойти gate. Документационные/data-only ТЗ остаются совместимыми.

### B2. preflight

Добавить аргумент `--inventory <prebuild_inventory.json>`.

Для нового кодового ТЗ preflight проверяет:

1. `feature_id` и `problem_id` совпадают с ТЗ;
2. `repo_head` совпадает с текущим `HEAD`;
3. fingerprint рабочей поверхности не изменился;
4. решение не `stop`;
5. выбранный владелец указан для `reuse/extend/port`;
6. для `new` есть `ABSENT_PROVEN`, а Graphify не устарел;
7. незакоммиченный конкурирующий код отсутствует.
8. schema/version, command hash, непустые queries и coverage всех семи стадий
   присутствуют; `skipped` допустим только с проверяемой причиной.

Любое расхождение требует нового inventory, а не ручного обхода.

Fingerprint определить однозначно как SHA-256 от: текущего `HEAD`, вывода
`git worktree list --porcelain`, `git status --porcelain=v1` каждого
проверенного worktree, tracked/staged diff и содержимого только тех untracked
кодовых файлов, которые совпали с входными символами/словами. Большие
untracked-данные не хешировать и не читать.

### B3. Защита от фиктивной галочки

Не принимать заранее созданный пустой JSON. Тест должен менять `HEAD`, diff или
untracked-кандидат после inventory и доказывать, что preflight останавливается.

Свежий вручную сфабрикованный JSON также не принимается: обязательны coverage,
непустые queries и evidence, которое preflight перепроверяет по path/sha.

## 6. Шаг C: не терять проблему между диалогами

Не создавать ручной отдельный реестр, который станет второй правдой.

Источники истины:

- заголовки ТЗ с `Feature-ID` и `Problem-ID`;
- итоговый audit manifest;
- код и Git;
- решения владельца в `DECISIONS_LOG`.

`project_now.py` должен генерировать раздел:

- открытые `Problem-ID`;
- активная попытка и её worktree/HEAD;
- последняя завершённая попытка;
- закрыта проблема или только попытка;
- следующий проверяемый шаг;
- конфликтующие параллельные ТЗ по одному `Feature-ID`.

Для нового формата ТЗ итог должен различать:

- `attempt_complete` — эта попытка закончена, проблема остаётся;
- `problem_closed` — критерий исходной проблемы выполнен;
- `blocked` — есть конкретный внешний блокер;
- `superseded` — продолжение ведётся другой попыткой.

Перенос файла в `_done` сам по себе не означает `problem_closed`.

Писатель исхода — `scripts/task_move.py`. Для нового формата добавить явный
аргумент `--outcome attempt_complete|problem_closed|blocked|superseded` и
поле `Исход:` в переносимом ТЗ. `project_now.py` только читает это поле. Для
старых ТЗ поведение оставить совместимым и показывать `legacy_unknown`.

## 7. Шаг D: расширить существующий Claude skill

Не создавать второй общий development-skill. Расширить

5. написать одну строку решения:

- не существует ли уже владелец функции;
- не является ли новый слой вторым источником истины;
- соответствует ли Graphify текущему `HEAD`;
- проверены ли dirty/untracked и невлитые ветки;
- закрывается ли исходный `Problem-ID`, а не один симптом.

## 8. Шаг E: воспроизводимый пакет Claude CLI

Не создавать новый общий pack-builder. Во втором атомарном под-ТЗ расширить
`make_audit_pack.py` режимом контекстного ревью.

Обязательный минимум пакета:

1. `task.md` — точное ТЗ вместе с критериями приёмки;
2. `prebuild_inventory.json` — включая отобранные Graphify/raw/git evidence;
3. `git_context.txt` — branch, HEAD, status, worktree и хеш diff;
4. `manifest.json` с SHA-256 всех файлов, записанный последним.

`previous_findings.md` допустим только для повторного аудита. Полные копии
source-of-truth документов и отдельный `graphify_evidence.md` не нужны: это
дубли пакета. Claude читает точные исходные пути, перечисленные в `task.md`.

Checkpoint хранить в итоговом manifest/audit pack, а не как отдельный постоянно
редактируемый источник истины. Обязательные поля:

- `feature_id`, `problem_id`, task path;
- branch, worktree, HEAD;
- изменённые файлы;
- выполненные тесты и их статус;
- открытые вопросы и стопы;
- запущенные внешние ревьюеры и hash их входа;
- следующий единственный шаг;
- флаги с владельцем и точкой закрытия.

Пакет не должен читать `~/.mango_secrets`, env-файлы, реальные клиентские
сообщения, полный Graphify-граф или runtime-данные. Текущий маскер
`make_audit_pack.py` гарантирует только телефоны и email; до отдельного
секрет-маскера нельзя утверждать, что он очищает произвольный токен.

До записи manifest выполнить fail-closed scan всех файлов пакета. Присваивания
ключей с суффиксами `_TOKEN`, `_SECRET`, `_API_KEY`, маркеры `Bearer`, `sk-`
и bot-token-подобные строки блокируют пакет, а не маскируются молча.

Старый `.claude` audit-pack entrypoint должен стать совместимым wrapper на
`scripts/make_audit_pack.py`, а не вторым builder.

## 9. Правило запуска Claude CLI

`claude auth status` в текущей среде может вернуть `loggedIn=false`, хотя
реальный вызов работает. Поэтому:

1. не запускать login только по `auth status`;
2. один раз за текущую задачу выполнить короткий обезличенный функциональный
   smoke в той же sandbox/escalated-среде, где пойдёт аудит;
3. повторный login не запускать, пока нет фактической auth-ошибки;
4. только при реальной auth-ошибке попросить Дмитрия войти один раз;
5. перед ручным повтором сравнить `prompt_hash + manifest_hash + HEAD` и не
   запускать одинаковый аудит без записанной причины.

Claude запускается read-only. Ему передаётся явный путь к пакету. Он обязан
назвать прочитанный `HEAD`, перечислить проверенные файлы и отделить факт от
гипотезы. Длинный чат Claude не является источником состояния.

## 10. Правила для D1, D2, D3 и M1

1. Один worktree — один исполнитель — одна крупная задача.
2. В checkpoint указывать владельца merge и порядок слияния.
3. Совпадение `Feature-ID` в двух активных ТЗ является стопом до разделения зон.
4. Реализация из другого диалога считается существующей, даже если она ещё не
   закоммичена; это класс `PARTIAL_WORKTREE`.
5. Правило проверки hash повторного аудита и субагента живёт в process skill и
   checkpoint текущей задачи, а не в новом персистентном сервисе.

## 11. Обязательные тесты

### Inventory

1. Находит точную реализацию в текущем tracked-коде.
2. Находит частичную реализацию в modified-файле.
3. Находит реализацию в untracked-файле.
4. Находит donor-код в невлитой ветке.
5. Отличает исторически удалённый код от кандидата на reuse.
6. Общие слова не дают ложный `FOUND`.
7. Устаревший Graphify не позволяет `ABSENT_PROVEN`.
8. Кандидат Graphify без подтверждения в сырье не считается найденным.
9. Не читает БД, аудио, почту и `stable_runtime`.
10. Повтор на неизменной поверхности детерминирован.

Пункт 9 доказывать мутационно: monkeypatch `sqlite3.connect` и чувствительные
read-helper'ы должны падать, если inventory попытается их вызвать.

### Preflight

1. Нет inventory — новая кодовая задача останавливается.
2. Сменился HEAD — останавливается.
3. Появился untracked-кандидат — старый inventory протух.
4. `decision=stop` — останавливается.
5. `reuse/extend/port` без selected owner — останавливается.
6. Любое взятое в работу ТЗ с зонами `src/` или `scripts/` без нового
   заголовка блокируется; docs/data-only legacy остаётся совместимым.
7. Свежий сфабрикованный JSON без coverage/evidence блокируется.

### Claude context

1. Manifest содержит SHA-256 всех файлов и записан последним.
2. Изменение любого файла ломает проверку пакета.
3. Телефон/email/секрет не попадает в пакет.
4. Полный Graphify-файл не копируется.
5. Токен, помещённый прямо в любой входной файл, блокируется до manifest.
6. Read-only smoke и инструкция авторизации проверяются ручным чек-листом;
   отдельное долговременное auth-состояние в коде не создавать.

### Сквозные проверки на реальных классах проекта

1. D3/Wappi: untracked `build_wappi_outreach_cases.py` обнаруживается как
   `PARTIAL_WORKTREE`, новое строительство блокируется.
2. D2/Calls: существующая карта ролей и слабый дублирующий валидатор попадают в
   один отчёт с решением владельца.
3. Bot: Graphify находит `SubscriptionLlmDraftProvider.build_draft`, а сырой
   код подтверждает настоящий direct-path entrypoint.

## СТОП

Немедленно остановиться, если:

1. для поиска функции предлагается второй сканер вместо расширения текущего;
2. требуется читать клиентские данные, БД, аудио или runtime;
3. найден пересекающийся dirty worktree без решения владельцев;
4. новый механизм предлагается при найденном `ACTIVE_*`, `PARTIAL_WORKTREE`
   или `DONOR_REF`;
5. Graphify устарел, а исполнитель заявляет `ABSENT_PROVEN`;
6. атомарный под-ТЗ превышает бюджет `AGENTS.md`;
7. тест требует live-write, ASR, AMO, Tallanto, Wappi-send или M1-run.

## Приёмка

Работа принята только если:

1. ни один новый общий сканер, task-tracker или feature-service не создан;
2. Graphify является первым шагом, но не доказательством отсутствия;
3. dirty/untracked работа видна;
4. невлитые ветки видны;
5. решение `new` невозможно без `ABSENT_PROVEN`;
6. новый код нельзя начать с протухшим evidence;
7. Claude получает один воспроизводимый пакет, а не пересказ диалога;
8. повторный одинаковый Claude-аудит и повторный login не запускаются;
9. `_done` больше не равен автоматическому закрытию проблемы;
10. три сквозных сценария раздела 11 зелёные;
11. полный безопасный pytest зелёный;
12. audit pack содержит self-review и независимый breaker-review.

## Порядок реализации: четыре атомарных под-ТЗ

### Под-ТЗ A1 — inventory, выполняется первым

1. Тестами зафиксировать текущие дефекты inventory, включая замену старого
   ассерта `status == "FOUND"` в `tests/test_skills_top5_tools.py`.
2. Убрать `build_project_inventory`, исправить Graphify-запросы и классы.
3. Добавить read-only обход всех worktree через существующий parser.
4. Добавить JSON/MD-отчёт, coverage и fail-closed классы.
5. Прогнать D3/Wappi, D2/Calls и bot-entrypoint сценарии.

### Под-ТЗ A2 — preflight и процесс, только после зелёного A1

1. Добавить `preflight --inventory` и перепроверку evidence.
2. Для любой ТЗ с кодовыми зонами `src/` или `scripts/` требовать новые поля.
3. Расширить Claude skill, architect-agent, короткие AGENTS/CLAUDE rules.
4. Добавить session-local dedupe-правило внешних ревью по входным hash.

### Под-ТЗ B — только после зелёного A2

1. Расширить `make_audit_pack.py` четырьмя файлами раздела 8.
2. Добавить SHA-256 manifest и проверку целостности.
3. Сделать `.claude` pack-скрипт совместимым wrapper канонического builder.
4. Проверить fail-closed secret scan и read-only Claude CLI handoff.

### Под-ТЗ C — только после зелёного A2

1. Добавить `--outcome` в `task_move.py` для новых ТЗ.
2. Добавить generated-раздел проблем в `project_now.py`.
3. Доказать, что `_done` не выдаётся за `problem_closed`.

Каждый под-ТЗ имеет отдельный preflight, тесты, audit pack, коммит и приёмку.
Красный A1 блокирует A2, B и C; красный A2 блокирует B и C.

## Бритва и бюджет

Рассмотрены варианты:

1. новая БД/сервис реестра функций — отклонён как второй источник истины;
2. новый общий Claude skill — отклонён как дубль существующего процесса;
3. расширение существующих четырёх точек — выбран минимальный вариант.

Бюджет каждого под-ТЗ:

- нетестовый код: до 150 добавленных строк;
- новая зависимость: 0;
- новый feature flag: 0;
- новый runtime/service: 0;
- новые tracked-файлы допустимы только для тестовых фикстур;
- превышение требует СТОП-формат из `AGENTS.md`, а не молчаливое раздувание.

## Что не делать

- не восстанавливать контекст из одного чата;
- не доверять одному `CLAUDE.md` как актуальной правде;
- не считать зелёный тест доказательством бизнес-готовности;
- не считать наличие файла доказательством, что функция вызывается;
- не считать отсутствие узла Graphify доказательством отсутствия кода;
- не сканировать клиентские данные ради поиска функции;
- не делать checkout чужого worktree;
- не удалять и не сливать найденный дубль автоматически;
- не запускать Claude с реальными переписками без отдельного разрешения;
- не обходить stop-gate ручным пустым JSON.

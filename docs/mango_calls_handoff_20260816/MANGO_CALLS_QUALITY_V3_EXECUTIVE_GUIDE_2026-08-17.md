# Mango Calls Quality v3: объяснение для руководителя

Дата: 2026-08-18. Основной выпуск Quality v3: `fb7eed42`. Дополнение Resolve D-122: `dea4a54b`. Подготовлено Codex, независимо проверено Claude. Документ написан для чтения без технического образования. Сложные слова расшифрованы при первом появлении.

## Что это за выпуск в одном абзаце

Система, которая слушает записи телефонных звонков, превращает их в текст и делает
короткий вывод для руководителя отдела продаж (РОП). Раньше вывод мог быть уверенным,
но недоказуемым: система сама решала, где менеджер, а где клиент, и писала «клиент
согласился оплатить», не имея на это подтверждения. Этот выпуск меняет правило:
**система имеет право называть стороны и делать коммерческие выводы только тогда,
когда есть доказательство. Нет доказательства — нет вывода, но и звонок не теряется.**

Побочный, но важный эффект: там, где вывод делать нельзя, платная модель вообще не
вызывается. Это экономит деньги, но экономия пока доказана как **механизм**, а не как
цифра. Точную цифру даст только пилот. 18 августа добавлен отдельный безопасный режим выборочного улучшения Resolve. Он по умолчанию выключен и не входит в живую службу до слепой проверки на 10, 50 и 100 уже распознанных звонках.

## Словарь (9 слов, дальше они используются без объяснений)

## Полный путь звонка по шагам

```text
1. Mango: скачивание записи и метаданных
        ↓
2. Ingest: запись заводится в рабочую базу
        ↓
3. Распознавание: Whisper + GigaAM (локально, на нашем железе)
        ↓
4. Resolve: сборка одного разговора из двух дорожек. По умолчанию без модели;
   режим selective пока выключен и после отдельной приёмки сможет сделать
   не более одного вызова только при существенном расхождении двух распознаваний
        ↓
5. Контракт диалога: реплики нумеруются T0001…, ставятся таймкоды,
   считается решение «роли доверенные / недоверенные»
        ↓
   ┌───────────────────────────────┬──────────────────────────────────┐
   │ роли НЕ доказаны              │ роли доказаны Mango              │
   │ (или звонок доказанно пустой) │                                  │
   ↓                               ↓                                  │
6a. Детерминированный результат:   6b. Analyse: один вызов Codex      │
    «Спикер A/B», полный текст,        (профиль compact)              │
    нейтральные темы, «нужна           ↓                              │
    проверка». Модель НЕ вызвана.  6c. Если ответ явно неполон —      │
                                        один вызов full (эскалация)   │
                                       ↓                              │
                                   6d. Проверка доказательств:        │
                                       вывод без ссылки на реплику    │
                                       удаляется                      │
   └───────────────────────────────┴──────────────────────────────────┘
        ↓
7. Нормализация текста и перевод времени в МСК (жёсткие правила, без модели)
        ↓
8. Учёт: закрытие записи попытки, запись результата в базу,
   только после этого ответ кладётся в кэш
        ↓
9. Выгрузка в Google: 17 столбцов, проверка баланса до записи,
   повтор без изменений = 0 записей. Модель не используется.
```

**Про повтор.** Есть два разных «повтора», их нельзя путать:

- **Повтор на уровне службы** — звонок не изменился, служба вообще не доходит до
  Analyse. Отчёт показывает `status=idle`, `stop_reason=unchanged_snapshot`,
  `new=0`, `reused=1`, `runs_resolve_analyze=false`. Расход = 0.
- **Прямой повтор Analyse** на том же входе — доходит до Analyse и попадает в кэш:
  `cache_hit=true`, 0 обращений к модели. Требовать `cache_hit=true` от повтора
  службы бессмысленно: она в Analyse не заходила.

## Где тратятся токены Codex, а где нет

| Шаг | Тратятся токены Codex? | Почему |
|---|---|---|
| 1. Скачивание записи из Mango | Нет | Обычный сетевой запрос по API, модели там нет. |
| 2. Ingest в базу | Нет | Работа с файлами и таблицей. |
| 3. Whisper + GigaAM | Нет токенов Codex | Это локальное вычисление на нашем компьютере. Стоит электричества и времени процессора, но не внешних денег. Путать эту нагрузку с токенами нельзя. |
| 4. Resolve в службе | **Нет в штатном режиме**; в выключенном `selective` — не более одного вызова | Значение по умолчанию — `off`. Режим `selective` существует в коде, но не разрешён для реальных звонков до слепой проверки 10 → 50 → 100. |
| 5. Контракт диалога и решение о ролях | Нет | Чистые вычисления: сравнение хэшей, сверка текстов, нумерация реплик. |
| 6a. Звонок с недоверенными ролями | **Нет, ровно 0** | Модель и кэш не трогаются вообще, результат собирается детерминированно. В учёте помечается `token_usage.source=skipped_untrusted_role`. |
| 6a. Доказанно несодержательный звонок (автоответчик, IVR, недозвон) | **Нет, ровно 0** — при штатной настройке | Решение принимается до модели, помечается `skipped_deterministic`. Важная оговорка: этот пропуск отключается переменной окружения `TELEGRAM_NON_CONVERSATION_ADVISORY`. Если её включить, такие звонки снова пойдут в модель. По умолчанию она выключена, но служба её не переопределяет принудительно — значит, её фактическое значение надо указывать в каждом отчёте о расходе. |
| 6b. Новый доверенный содержательный звонок | **Да, один вызов** | Профиль `compact`, версия промпта `v8`. Это единственный обязательный платный шаг. |
| 6c. Эскалация compact → full | **Да, ещё один вызов, но только по явному условию** | Если ответ compact не заполнил ни одного поля, либо не увидел явно присутствующий продукт/предмет/следующий шаг, либо назвал реальный разговор пустым — задаётся второй вопрос по расширенному промпту `v9`. Это **не** повтор при ошибке: технический сбой в вызов не превращается, он попадает в очередь отдельно. По умолчанию условие эскалации включено. |
| 6b/6c. Повторный тот же вход | Нет | Кэш отдаёт готовый ответ. |
| 7. Нормализация текста и МСК | Нет | Словарь жёстких правил, без модели. |
| 8. Учёт попыток и баланс | Нет | Запись в базу и арифметика. |
| 9. Выгрузка в Google | **Нет** | В выгрузчике нет ни одного обращения к модели — проверено по исходникам обоих скриптов публикации. |

**Граница этого утверждения:** в проверенном коде штатное значение Resolve остаётся `off`, поэтому обращений к модели нет. Режим `selective` уже реализован, но на M1 ещё не развёрнут и не разрешён для реальных звонков. Его качество, доля срабатываний, задержка и расход должны быть измерены на неизменных копиях уже сохранённых ASR-результатов.

**Отдельно и честно:** Codex CLI в текущем виде **не возвращает точное число токенов**.
Поэтому система пишет `token_usage=unavailable` и не выдумывает оценку по количеству
символов. Это сознательное решение: неверная цифра в отчёте о расходах хуже честного
«провайдер не сообщил». Точные числа появляются только у провайдеров, которые их
возвращают (например, OpenAI), — там они помечаются `provider_exact`.

## Что действительно экономит токены (доказано кодом)

1. **Недоверенные роли — ноль обращений.** Раньше понятия «доказаны стороны» не
   существовало вовсе: модель вызывалась на каждом звонке, и её выводы публиковались,
   даже когда было неизвестно, кто менеджер. Теперь такой вывод публиковать нельзя —
   значит и платить за него незачем, модель не вызывается.
2. **Доказанно несодержательные звонки — ноль обращений.** Автоответчик, IVR,
   недозвон отсеиваются до модели.
3. **Resolve по умолчанию не вызывает модель.** Раньше на спорном звонке модель могла вызываться отдельно для каждой дорожки. Теперь штатный режим даёт 0 обращений, а пока выключенный `selective` ограничен максимум одним обращением на весь звонок. Это снижает потолок расхода, но реальную экономию ещё надо измерить.
4. **Повтор неизменного звонка ничего не стоит.** На уровне службы он не доходит до
   Analyse; прямой повтор Analyse попадает в кэш.
5. **Один зарезервированный вызов = ровно одно внешнее обращение.** Скрытых повторов
   внутри одной задачи Analyse нет: технический сбой фиксируется и возвращается в
   управляемую очередь, а не превращается в тихие 2–5 обращений.
6. **Выгрузка в Google не использует модель вообще.**
7. **Модель больше не пишет свободный конспект** — служба собирает конспект сама из
   подтверждённых значений. Это уменьшает объём того, что модель пишет в ответ.

## Что пока НЕ доказано (и не надо обещать)

1. **Суммарный расход в рублях.** Codex не возвращает токены, поэтому «минус N%
   токенов» сказать нельзя ни сейчас, ни после пилота — можно измерить только
   **число обращений** к модели и сверить его с биллингом провайдера.
2. **Итог по одному доверенному звонку заранее неизвестен.** Здесь две силы тянут в
   разные стороны, и обе реальны. Вверх: сам шаг Analyse стал дороже — вход богаче
   (у каждой реплики появился номер и таймкод), контракт требует от модели отдельную
   ссылку-обоснование на каждое заполненное поле, и иногда добавляется второй вызов
   `full`. Вниз: с того же звонка убраны обращения Resolve. Что перевесит на реальных
   звонках — **не измерено**. Обещать снижение стоимости каждого содержательного
   звонка нельзя; надёжно экономия видна на массе, где много звонков вообще не
   вызывают модель.
3. **Первый проход после этого выпуска — холодный.** Версия промпта изменилась
   (`v6→v8` для compact, `v7→v9` для full). Изменение модели, версии промпта, входа
   или параметров запуска меняет ключ кэша, поэтому старые совпадения не сработают.
   Массовый повтор истории до согласованного бюджета запрещён.
4. **Доля эскалаций compact → full неизвестна.** Если она окажется высокой, расход
   вырастет вдвое на этих звонках. Её надо измерить на 10 и 50 звонках.
5. **Качество выводов на реальных звонках не измерено.** Тесты зелёные — это только формальная исправность. Для нового `selective` Resolve 435 тестов и аудит Claude подтверждают защитный каркас, но не доказывают, что текст на реальных звонках становится лучше. Нужна слепая проверка 10 → 50 → 100 с нулём выдумок.

## Самое важное ограничение, которое нельзя пропустить

Прямо сейчас, на этом коде, **ни один реальный звонок не может стать «доверенным»**.
Причина не в ошибке, а в порядке работ: система требует официальный ответ Mango с
разметкой сторон, а слой захвата записей его пока не сохраняет. Проверка честно
возвращает причину `provider_evidence_missing`.

Практическое следствие, которое надо понимать до включения:

- если запустить выпуск как есть, **100% звонков пойдут по безопасному пути**:
  «Спикер A/B», полный текст, нейтральные темы, пометка «нужна проверка»;
- в таблице **не будет** результата, возражения, следующего шага и срока;
- расход на модель при этом будет близок к нулю — но и коммерческой пользы для РОПа
  тоже не будет.

Поэтому доработка захвата ответа Mango на M1 — не улучшение, а **обязательное
условие**. До неё выпуск даёт безопасность и честность, но не даёт выводов.

# P0: модель вместо смысловых регулярных выражений

Каноническое исходное ТЗ:
`/Users/dmitrijfabarisov/Claude Projects/Foton/2026-07-29_TZ_P0_regex_to_LLM.md`.

## Цель

Довести P0-классификацию до одного понятного механизма:

1. модель в существующем вызове определяет `is_p0` и `p0_kind`;
2. отсутствие физического поля `is_p0` закрывается в сторону менеджера;
3. узкая детерминированная страховка может только добавить P0;
4. защёлка P0 на диалог, аудит и выходные полы сохраняются;
5. старые смысловые P0-словари удаляются только после сравнительного PASS на M1.

## Обязательный порядок

### Этап 1. Тень без изменения поведения

- Зафиксировать старый и модельный вердикты в неперсональных метаданных.
- Не менять маршрут, текст, число модельных вызовов и действующий P0-пол.
- Там, где ранний блок не вызывает модель, не добавлять вызов в рабочий путь:
  полное сравнение выполняется офлайн на M1.
- Подготовить отчёт расхождений и пакет запуска M1.

### Контрольная точка M1-1

- Принять независимый честный набор, который готовит Claude Code на M1.
- Проверить независимость, знаменатель 27 507 и слепую переразметку.
- До этого этапы 2-4 не начинать.

### Этапы 2-4. Переключение

- Убрать ранний словарный блок сначала для класса возврата.
- Сделать физически присутствующее поле `is_p0` решающим.
- При отсутствии поля закрывать маршрут в `manager_only`.
- Ввести одну узкую страховку для бесспорных юридических угроз, буквальной
  жалобы, чарджбека и безопасности ребёнка.
- Не добавлять модельных вызовов, файлов, зависимостей или постоянных флагов.
- Сохранить откат через существующий `TELEGRAM_P0_MODEL_LED=0` до экзамена.

### Контрольная точка M1-2

- Парный экзамен старое/новое на независимом наборе и реальном корпусе.
- P0 recall не хуже старого; ложные P0 ниже; P0/brand/PII/number hard-zero.
- Проверить стабильность минимум тремя повторными разметками спорных кейсов.

### Этап 5. Удаление

- Только после M1 PASS удалить поглощённые словари и ветки.
- Не удалять тестовые наборы, защёлку P0, журнал аудита, выходные P0-полы,
  бренд-, ПДн- и числовые защиты.
- Повторить полный pytest и смысловой аудит.

## Неотменяемый критерий готовности каждого этапа

1. Цепочка боевого вызова с `файл:строка`.
2. Сквозной сценарий через `SubscriptionLlmDraftProvider.build_draft()`.
3. Отрицательный контроль: намеренно сломанная функция меняет сквозной вывод.
4. Числитель и знаменатель; для трафика знаменатель 27 507.
5. Независимый набор не меняется вместе с кодом.
6. Явный откат.

## Приёмка

- Этап 1: сквозные тесты доказывают неизменность маршрута, текста и числа
  модельных вызовов; диагностические метаданные содержат оба вердикта без ПДн.
- Этапы 2-4: независимый M1-экзамен подтверждает нулевые жёсткие нарушения,
  полноту P0 не хуже старого пути и меньше ложных переводов менеджеру.
- Этап 5: поглощённый код удалён, полный pytest зелёный, смысловой аудит PASS,
  остаётся одна P0-архитектура с документированным откатом.

## СТОП

- Независимый набор M1 не принят или его разметка расходится более чем на 10%.
- Новый путь пропускает подтверждённый P0, смешивает бренды, раскрывает ПДн,
  выдумывает числа или увеличивает число модельных вызовов.
- Отрицательный контроль не меняет сквозной результат.
- Нужна запись во внешнюю систему, рабочую базу или включение Wappi.
- Появились чужие изменения в файлах текущего блока.

## Ограничения

- Wappi остаётся выключенным.
- Никаких внешних записей и изменений рабочих баз.
- Большие модельные замеры выполняются только на M1.
- Текущий сбор Customer Timeline не останавливать и не менять.

# M1 Calls: довести подготовленный контур до работающей службы

## 1. Бизнес-цель

Не строить ещё один конвейер. Использовать уже работающие Whisper, GigaAM,
Resolve и Analyze и за минимальное число шагов получить службу на M1, которая:

1. каждые 15 минут проверяет Mango и скачивает только новые записи;
2. дважды в час строго последовательно выполняет
   `Whisper large-v3 -> очистка MLX -> GigaAM v2 -> Resolve -> Analyze`;
3. после сбоя продолжает с незавершённой стадии и не повторяет готовую;
4. не теряет и не дублирует звонки;
5. показывает сотрудникам понятную строку в приватной Google Таблице;
6. даёт РОПу полный последовательный диалог через закрытый Яндекс.Диск;
7. обновляет только отдельную staging-базу Customer Timeline;
8. не пишет в AMO, Tallanto и production Customer Timeline.

Первая реальная польза должна появиться после контрольных 10 звонков, а не
после очередного большого архитектурного цикла.

## 3. Жёсткие границы

- Не писать новый параллельный конвейер и не оставлять два пути обработки.
- Не менять модели: Whisper large-v3 MLX и GigaAM v2 остаются утверждёнными.
- Не запускать две модели одновременно.
- Не включать fallback на более слабую модель молча.
- Не запускать Mango API, ASR, Resolve, Analyze, launchd, перенос runtime или
  внешнюю публикацию до отдельного явного подтверждения Дмитрия для
  соответствующего шага.
- Не передавать через Git секреты, SQLite, аудио, транскрипты и ПДн.
- Не удалять старый runtime. До окончания пилота он является откатом, но его
  автоматические задания должны быть штатно выключены при cutover.
- AMO, CRM, Tallanto write и production Customer Timeline не входят в работу.
- Полный исторический перенос аудио выполнять только после стабильного сервиса.
- Не добавлять новые общие абстракции, флаги и зависимости без доказанного
  блокера текущего живого пути.

## 4. Выполнить одним потоком

### 4.1. Сделать результат M1 проверяемым на основном Mac

До любого live-действия:

1. Проверить чистоту worktree M1 и точный `HEAD`.
2. Передать через Git Яндекс.Диска ветку и убедиться с основного Mac, что
   удалённая ссылка равна `86ea485...` или более новому явно указанному SHA.
3. Если синхронизация каталога Git ненадёжна, дополнительно создать обычный
   `git bundle` только с кодом, рядом SHA-256 и положить его в закрытую папку
   передачи. В bundle не должно быть runtime и ПДн.
4. Передать обезличенный audit pack с `manifest.json`, сырым выводом тестов,
   changed files и пятью отдельными статусами. Audit pack не коммитить.
5. На основном Mac независимо проверить parent, diff от `655bf6b9`, чистоту и
   целевые тесты. Пересказ автора не считается доказательством.

**Приёмка:** точный commit доступен на обоих Mac; SHA совпадает; audit pack
читается; нет секретов/ПДн; тесты воспроизводятся.

### 4.2. Закрыть только оставшиеся корневые пробелы

На точном новом SHA заново доказать следующие классы. Если механизм уже есть,
не переписывать его, а приложить сырой тест и живой путь.

#### A. Независимая полнота Mango

Нельзя объявлять ответ API полным только потому, что HTTP-запрос успешен.
Нужно сверять объединение звонков двумя независимыми разбиениями периода либо
официальным total/page-контрактом Mango, если он действительно доступен.

Закрытый баланс каждого прохода:

`сырые записи Mango = уникальные звонки + доказанные дубли + без записи/карантин + ошибки + необъяснённые`.

Для зелёного результата `необъяснённые=0`. Неизвестная страница, усечение,
разрыв окна или расхождение двух проходов запрещают продвигать cursor.
«Неизвестная страница» относится только к постраничному API. Для используемой
stats-выгрузки Mango эквивалентны неготовый/усечённый файл результата,
исчерпание polling-дедлайна или расхождение двух разбиений.
Обязательны тесты границы окна, одинакового времени, поздней записи, повторного
call_id и нескольких записей одного звонка.

Закрытый баланс обязателен для каждого прохода. Независимое второе разбиение
обязательно при закрытии московских суток, догоне и сверках 7/30 суток. Для
обычного 15-минутного прохода достаточно безопасного перекрытия, баланса и
честного `capture_status=partial`, если источник не дал финального доказательства.

#### B. Закрытие тихих суток

Новое доказательство полного или нулевого прохода обязано создавать новую
версию ready-manifest даже при неизменной SQLite и capture-manifest. Два
независимых нулевых прохода после конца московских суток должны закрывать день
без ожидания следующего звонка.

#### C. Раздельные допуски

Должны существовать два разных статуса:

- `ready_for_controlled_one`: изолированные среда/БД, доступ, SHA, диск, модели
  и snapshot достаточны; production cutover и замер десяти ещё не нужны;
- `ready_for_permanent_service`: дополнительно есть controlled-10, запас 2x,
  память, публикация, внешний наблюдатель и пилот.

Пустой controlled-10 обязан разрешать один звонок и запрещать постоянную службу.

#### D. Память и процессы

Swap, RSS и число процессов входят в обязательный контроль. При каждой стадии:

- одновременно существует только один тяжёлый worker;
- Whisper завершается до GigaAM;
- после Whisper вызывается очистка MLX;
- через 10 минут RSS/swap не выше чем на 10% относительно baseline, снятого
  readiness-probe непосредственно перед циклом;
- timeout завершает всю группу и не оставляет дочерние процессы;
- устойчивый рост swap или красное memory pressure останавливают расширение.

#### E. Реальная публикация, а не локальный план

После отдельного разрешения служба должна вызывать реальные идемпотентные
writer-ы Google и Яндекс.Диска. Для каждого назначения хранить состояния
`planned -> written -> readback_ok`. Ошибка одного назначения не создаёт дубль
в другом и остаётся видимой для повтора.

Google «Сегодня»:

- одна строка на `call_key`, повтор обновляет её, а не добавляет дубль;
- точное ФИО менеджера из утверждённого справочника
  `Mango ID/добавочный -> ФИО`;
- ФИО клиента заполняется только при разрешённом точном однозначном совпадении;
  без такого доступа или при неоднозначности писать «Не подтверждено», не
  угадывать имя и не блокировать первый пилот;
- краткое содержание содержит 1-5 полных предложений по фактическому объёму
  разговора; тема, итог, риск, следующий шаг и срок указываются только когда
  они действительно известны;
- текст не обрезается многоточием и не повторяет соседние поля;
- комментарии и решения РОПа сохраняются при обновлении;
- готовая строка получает уже поддерживаемую приватную ссылку Google Drive на
  конкретный полный TXT с `acl_readback_ok`.

Ограничение в 300 символов не вводить: оно снова сделает текст куцым. Критерий
не длина, а чтение за 20-30 секунд и отсутствие выдумок. Полный Analyze и полный
диалог остаются в защищённых артефактах.

Яндекс.Диск:

- один полный TXT на звонок без сокращений и перестановки реплик;
- имя файла не содержит телефон; связь идёт через `call_key` и manifest;
- тот же TXT и суточный XLSX записываются существующим экспортом в приватную
  папку; новый Яндекс-uploader и URL-механизм не создавать;
- существующее доказательство `mango_yandex_publication_authority_v1` подтверждает
  `private_acl_readback_ok`, а hash TXT совпадает с Google Drive-файлом;
- публичная ссылка запрещена.

Не ослаблять общий запрет размещать рабочую SQLite, секреты и временные файлы
конвейера внутри синхронизируемых каталогов. Разрешить только узкий итоговый
каталог публикации TXT/XLSX, уже прошедший ПДн/ACL-гейт. Телефон допустим в
приватной Google-таблице как явно требуемое РОПом внутреннее поле, но запрещён
в именах файлов, URL, открытых логах и обезличенных audit pack.

#### F. Внешний наблюдатель

Локальный watchdog не доказывает, что выключенный M1 будет замечен. На время
пилота наблюдателем является основной Mac Дмитрия: M1 готовит сборщик
observation-JSON и инструкцию, а Дмитрий отдельно разрешает установку. Первичный
канал пилота — локальное уведомление macOS и status-файл; более дальний канал
оформляется отдельно и не блокирует контрольные 10. Наблюдатель
проверяет heartbeat, SHA, возраст watermark, состояние launchd, свободный диск
и отсутствие активного старого обработчика. Остановка M1, сети или launchd
должна дать реальное уведомление ответственному в пределах 30 минут.

`locked`, повторяющийся `deferred` и старый watermark не считать прогрессом.
Три последовательных `deferred` или превышение SLA очереди должны создавать
уведомление с владельцем и следующим действием. Карантин и dead-letter не могут
быть вечным складом: у каждой причины есть повторяемость, ответственный и срок
разбора, при этом сомнительная запись не публикуется как готовая.

До контрольного одного звонка обязательны A-D. E требуется перед контрольными
10 и их внешней публикацией, F — перед суточным запуском.

### 4.3. Развернуть runtime M1 без запуска обработки

После отдельного подтверждения Дмитрия на подготовку owner-only runtime, но без
Mango API, ASR, Resolve, Analyze, launchd и внешних записей:

1. Создать owner-only Python 3.12 venv в `$HOME/.mango_local`.
2. Установить только уже утверждённые зависимости из проекта.
3. Проверить `ffmpeg`, `ffprobe`, Codex CLI и подписочную авторизацию без текста
   звонков в выводе.
4. Проверить веса Whisper и GigaAM, их revision/hash и локальную доступность.
5. Создать config/env из шаблонов: каталоги `0700`, файлы `0600`.
   Секреты Mango, Tallanto, Google и Яндекс Codex не создаёт и не запрашивает в
   переписке: Дмитрий кладёт их в `~/.mango_secrets/` на M1 отдельным действием;
   Codex готовит только шаблон и список обязательных ключей.
6. Записать точный code SHA, host_id, модельные версии и пути под `$HOME`.
7. Проверить не менее 60 GiB свободного места и прогноз хранения на 14 дней.
8. Отрисовать launchd plist только в preview-каталог. Не устанавливать.
9. Выполнить read-only `ready_for_controlled_one` probe.

До постоянной службы добавить политику диска без автоматического удаления:
ежедневный прогноз, предупреждение при 60 GiB и hard stop при 40 GiB. Перенос или
удаление старого аудио разрешается только после hash/readback архива на
Яндекс.Диске и отдельного решения Дмитрия.

**Приёмка:** probe зелёный для одного звонка; никаких Mango/ASR/R+A вызовов,
launchd и внешних записей не произошло.

### 4.4. Контрольный один звонок в изолированном runtime

После отдельной команды Дмитрия на один реальный звонок. Эта команда разрешает
только для зафиксированного закрытого окна: read-only запрос Mango, скачивание
одной allowlisted записи и её ASR+Resolve+Analyze; остальные звонки не скачивать
и production cursor не менять.

1. Использовать отдельную staging-БД и фиксированное закрытое окно. Не менять
   production cursor и не останавливать старый Mac.
2. Выбрать один новый содержательный звонок с записью и двумя дорожками.
   Controlled-one обязан принимать явный allowlist одного `provider_call_id`
   и `expected_count=1`; широкий временной диапазон не считается контролем.
3. Выполнить полный путь локально на M1:
   capture -> Whisper -> очистка -> GigaAM -> Resolve -> Analyze -> ready DB ->
   Timeline staging -> локальный preview Google/Yandex.
4. Записать время, RSS, swap, модели, версии prompt и PID каждой стадии без ПДн.
5. РОП вручную сравнивает аудио, полный диалог и краткое содержание.
6. Повторить запуск на том же состоянии.

**Приёмка:** 1/1 звонок готов; роли не перепутаны; диалог полный; сводка без
выдумки; повтор даёт `downloaded=0`, `ASR=0`, `Resolve=0`, `Analyze=0`, дублей
строк/файлов 0. В отчёте явно: `allowed_call_key`, `attempted=1`, `processed=1`,
`attempted_other=0`; все остальные строки и стадии до/после неизменны.

### 4.5. Контрольные 10 звонков и первая бизнес-польза

После PASS одного звонка и отдельного подтверждения Дмитрия на этот batch
обработать 10 разных звонков: входящие/исходящие,
короткие/длинные, разные менеджеры, один несостоявшийся и один спорный матч
клиента.
Набор фиксируется allowlist из 10 `provider_call_id` и `expected_count=10` до
запуска; одиннадцатый звонок не должен попасть в тяжёлые стадии.

После отдельного разрешения опубликовать эти 10 строк в приватную тестовую
Google Таблицу и TXT в закрытый Яндекс.Диск.

**Приёмка:**

- баланс 10/10 закрыт, необъяснённых 0;
- 10 уникальных call_key, дублей 0;
- все 10 классифицированы как `ready_recorded`, `explained_no_recording` или
  `quarantine`; проблемная запись не может просто исчезнуть из таблицы;
- не менее 8 из 10 имеют статус `ready_recorded` и реально показаны РОПу;
- для всех `ready_recorded` правильны роли и менеджеры, есть полный TXT и ссылка;
- ложных ФИО клиента 0;
- все ссылки `ready_recorded` ведут на правильный полный TXT;
- анонимный доступ закрыт;
- все содержательные строки понятны РОПу за 20-30 секунд;
- критических смысловых ошибок 0;
- все записи получили объяснимый конечный статус не позднее 4 часов; `pending=0`;
- сроки считаются от постановки звонка в очередь M1;
- в таблице есть контроль `получено / готово / без записи / карантин / ожидает /
  необъяснимо`; `ожидает=0`, `необъяснимо=0`;
- swap/RSS возвращаются к согласованному baseline;
- повтор не вызывает тяжёлые стадии и не создаёт внешние дубли.

Если это выполнено, первая бизнес-польза считается полученной. Не ждать
семидневного испытания, чтобы дать РОПу контролируемый доступ.

### 4.6. Перенести точку продолжения и одновременно переключить capture

Полный перенос 5 248 исторических строк не является условием первых 10 звонков.
После их смыслового PASS и отдельного подтверждения выполнить единый cutover:

1. Подготовить relocation в dry-run, пока старый Mac продолжает быть владельцем.
2. Зафиксировать на старом Mac количество `N`, полный набор `(call_id, status)`,
   SHA, host_id, cursor, manifests, hashes, `quick_check`, `integrity_check` и
   счётчики незавершённых стадий.
3. Одним разрешённым окном штатно остановить старый capture, снять финальный
   delta/snapshot и передать напрямую по SSH/rsync, не через Git/Яндекс:
   - working DB, manifests, cursor/evidence;
   - аудио всех незавершённых строк и безопасного перекрытия 72 часа;
   - конфигурацию без секретов; ранее подготовленные секреты остаются только в
     owner-only каталоге M1 и не входят в перенос.
4. Применить relocation с manifest/crash-resume, сверить hashes и SQLite.
5. Включить только M1 capture. Старый runtime не удалять, но его launchd и env
   сделать недоступными для автоматического старта.
6. Если M1 не дал heartbeat и успешный capture за 30 минут, остановить M1 и
   выполнить документированный обратимый возврат старого владельца.

**Приёмка:** на M1 ровно `N` исходных call_id/status плюс явно учтённый финальный
delta; пути существуют; потерь/дублей 0; одновременно работает один capture;
перезагрузка старого Mac не запускает его автоматически.

### 4.7. Закрыть разрыв после 3 августа

После отдельного разрешения на read-only Mango API:

1. Зафиксировать закрытую верхнюю границу `until_utc` и безопасное начало не
   позже `2026-08-01T00:00:00+03:00`.
2. Дважды получить один и тот же закрытый интервал разным разбиением окон. Новые
   звонки после `until_utc` в сравнение не входят.
3. Скачать только отсутствующие записи атомарно, обновить manifest/cursor только
   после закрытого баланса и повторить диапазон: неизвестных новых должно быть 0.
4. Сначала обрабатывать свежий интервал, исторический догон брать ограниченными
   окнами тем же worker. Новую систему очередей не вводить без измеренного SLA.

До суточного запуска добавить ежедневную сверку последних 7 суток и еженедельную
сверку последних 30 суток без повторного ASR готовых call_id. На этом шаге не
запускать ASR/R+A, если разрешение дано только на Mango API.

### 4.8. Одни полные сутки

После отдельного разрешения установить временные launchd-задачи с автоматическим
сроком остановки через 24 часа:

- capture: `:00/:15/:30/:45`;
- тяжёлый цикл: `:07/:37`;
- локальный watchdog: не реже 15 минут;
- Google «Сегодня»: после каждого успешного Analyze, не позднее 60 минут;
- сначала Google Drive TXT upsert и ACL readback, затем Яндекс TXT/XLSX и
  hash/ACL readback, и только после этого Google Sheet upsert со ссылкой;
- закрытие предыдущего московского дня: повторные попытки в 06:00, 07:00,
  08:00; статус до 09:00.

До старта суток доказать запас не менее 2x от измеренного пика, внешний
наблюдатель и сверки 7/30 суток. РОП читает `min(30, ready_count)` случайных
звонков и все строки с предупреждениями по фиксированной рубрике: личность,
роли, полнота, тема, итог, риск, следующий шаг, отсутствие выдумки. Строка
проходит, только если верны все применимые пункты. `semantic_accuracy =
прошедшие строки / случайно выбранные ready-строки`; при знаменателе меньше 20
требуется 100%, иначе не менее 95%. Предупреждения проверяются отдельно и в
знаменатель не подмешиваются.

**Приёмка суток:**

- `Mango unique = ready + без записи + quarantine + pending + ошибки`,
  пересечения 0, необъяснённых 0;
- необъяснённых пропусков и дублей 0;
- не менее 95% записей скачаны за 45 минут;
- не менее 90% полностью готовы за 2 часа, не менее 99% за 4 часа;
- сроки считаются от конца звонка по данным Mango;
- растущей очереди нет;
- Google и Яндекс readback зелёные;
- критических ошибок РОПа 0, общая смысловая точность не ниже 95%;
- уведомление о тестовой остановке реально доставлено;
- тихий день и закрытие суток доказаны отдельным тестом/evidence.
- `launchctl print`, PID, cwd, SHA, env-фингерпринт и heartbeat подтверждают
  именно утверждённый worktree; каждый лог ротируется при 20 MiB, хранится не
  более 10 файлов и 14 суток, ПДн отсутствуют.
- после `expires_at` нет загруженных labels, PID, нового heartbeat и capture.

### 4.9. Три дня РОПа и постоянная служба

После суточного PASS запросить отдельный временный допуск на 72 часа с новым
`expires_at`. Продолжить тот же контур три последовательных дня, не расширяя
функционал; постоянный launchd пока запрещён.

**Приёмка:**

- три дня без потерь, дублей и растущей очереди;
- по `min(30, ready_count)` ручных проверок в сутки плюс все предупреждения;
- смысловая точность не ниже 95%; критических ошибок личности, оплаты,
  обязательства, результата и следующего шага 0;
- восстановление после одной штатной перезагрузки доказано;
- внешний наблюдатель реально замечает остановку;
- ежедневный закрытый баланс и обе публикации зелёные;
- AMO и production Timeline по-прежнему OFF.

После этого запросить отдельное финальное подтверждение Дмитрия и только затем:

1. убрать 24-часовой срок остановки;
2. установить постоянные launchd-задачи;
3. сохранить rollback snapshot и команду полного выключения;
4. обновить операторский статус и архитектурный DOCX;
5. наблюдать семь дней, не задерживая уже работающую бизнес-функцию.

Полный исторический перенос аудио оформить отдельным ТЗ после трёхдневной
приёмки. Он не входит в критический путь запуска службы.

## СТОП

Немедленно остановить расширение, но не удалять данные, если:

- новый SHA не доступен независимо или worktree грязный;
- старый и M1 capture могут работать одновременно;
- cursor продвинут при незамкнутом балансе;
- найден необъяснённый пропуск или дубль;
- роли дорожек перепутаны;
- модель запущена параллельно с другой тяжёлой моделью;
- swap/RSS растут после завершения стадий;
- SQLite integrity/quick check не `ok`;
- Google/Яндекс доступны постороннему;
- ссылка ведёт не на тот звонок или hash не совпадает;
- публикация меняет комментарии РОПа;
- внешний watcher молчит при остановке;
- свободно менее 40 GiB или предупреждение при менее 60 GiB не разобрано;
- обнаружена запись в AMO, Tallanto или production Timeline.

## 6. Обязательные тесты и проверки классов

Каждый подтверждённый пробой оставить постоянной проверкой:

1. неполный HTTP 200 Mango не продвигает cursor;
2. разные разбиения окон дают одинаковое множество call_id;
3. поздний звонок попадает через перекрытие;
4. тихий день обновляет ready evidence;
5. один звонок разрешён без controlled-10;
6. постоянная служба запрещена без controlled-10;
7. swap участвует в hard gate;
8. timeout не оставляет дочерний процесс;
9. завершённая стадия не повторяется после падения;
10. незавершённая стадия возобновляется;
11. old Mac + M1 одновременно блокируются;
12. Google upsert не создаёт дубль и сохраняет поля РОПа;
13. неизвестное/неоднозначное ФИО не угадывается;
14. каждая готовая строка имеет проверенную приватную Drive-ссылку на TXT, а тот
    же TXT подтверждён в Яндекс-доказательстве по hash;
15. ошибка Google не дублирует Яндекс и наоборот;
16. остановка M1 вызывает внешнее уведомление;
17. повтор неизменного состояния почти пустой;
18. никакой live-код не пишет в AMO/Tallanto/prod Timeline.
19. запись, появившаяся позже 72 часов, не теряется и не пересчитывает готовое;
20. накопление `deferred`, quarantine и dead-letter вызывает наблюдаемый разбор;
21. заполнение диска предупреждается заранее и никогда не запускает удаление.

Проверить существующие границы падения тестовыми инъекциями после получения
Mango, записи аудио, append manifest, claim/commit каждой тяжёлой стадии, ready
DB, ready manifest и внешней записи. Не добавлять production crash-hooks только
ради теста. Два повтора должны приводить к одному конечному результату.

## 7. Итоговые артефакты

M1 должен передать:

1. точную ветку, SHA, parent и чистый status;
2. diff относительно `655bf6b9` и отдельно относительно `86ea485...`;
3. воспроизводимый тестовый вывод;
4. обезличенный audit pack с manifest;
5. relocation manifest и закрытый баланс без идентификаторов клиентов;
6. controlled-one и zero-repeat отчёты;
7. controlled-10 измерения и ручную смысловую проверку;
8. суточные и трёхдневные verdict-файлы;
9. Google/Yandex readback и ACL-проверку без ПДн в открытом отчёте;
10. внешний watchdog proof;
11. launchd preview, затем startup manifest постоянной службы;
12. rollback-команду и операторский статус;
13. обновлённые русские runbook и DOCX.

Для каждого выпуска отдельно указать:

- `formal_pass`;
- `semantic_pass`;
- `business_pass`;
- `data_pass`;
- `runtime_pass`.

`business_pass=true` допустим только после реальной выдачи РОПу, `runtime_pass`
только после трёх дней, а `production_ready` только после отдельного решения
Дмитрия.

## 8. Что не делать

- Не запускать повторное распознавание всей истории.
- Не переносить сейчас весь исторический аудиоархив.
- Не улучшать модели и промпты вне ошибок контрольной выборки.
- Не строить новый dashboard, API или общий оркестратор.
- Не подключать AMO.
- Не объединять эту задачу с Customer Timeline production или другими треками.
- Не ждать идеальной инфраструктуры, если контрольные 10 уже дают безопасную
  бизнес-пользу РОПу.

# ТЗ-03. Проверяемые бизнес-факты с привязкой к репликам

Статус: проект, реализация запрещена до отдельного подтверждения Дмитрия.

Зависимости: `turn_id`/SHA из ТЗ-01 и role guard из ТЗ-02.

## 1. Простыми словами

Каждый важный вывод системы должен отвечать на вопрос: «Где именно в этом разговоре это сказано?»

Если конспект утверждает «менеджер отправит расписание завтра», рядом должны существовать точная реплика, её таймкод и ссылка именно на поля «Следующий шаг» и «Срок». Если ссылка отсутствует, ведёт на другой звонок или реплика не подтверждает поле, система не публикует это как факт и просит проверку.

Это не исправляет ошибку распознавания речи, но предотвращает уверенные выдумки Analyse и позволяет быстро проверить результат по аудио.

## 2. Доказательство проблемы

Проверено 15.08.2026 только чтением:

- `evidence=[]` у всех проверенных готовых Analyse (`1 700+` из `1 700+`);
- production prompt v2 не требует доказательств конкретных полей: `src/mango_mvp/services/analyze.py:35-100`;
- тест `tests/test_analyze.py:683-685` закрепляет отсутствие evidence в prompt;
- `_extract_evidence()` в `analyze.py:529-547` выбирает до трёх подходящих строк, но не связывает их с классом, суммой, обещанием или следующим шагом;
- текущий Analyse часто получает монолит без таймкодов, поэтому даже общий извлекатель ничего не находит;
- при сжатии текущий путь удаляет/режет элементы как строку, а не сохраняет устойчивые ссылки на целые реплики.

Следовательно, сейчас можно увидеть красивый конспект, но нельзя машинно доказать происхождение его бизнес-фактов.

## 3. Граница ТЗ

- Новая таблица или отдельная evidence-БД не создаётся.
- Доказательства хранятся внутри существующего `analysis_json`.
- Raw transcript, dialogue lines, Whisper/GigaAM/Resolve не изменяются.
- Google не меняется до ТЗ-05.
- Наличие цитаты не объявляется доказательством правильности ASR: это доказательство происхождения вывода из сохранённой расшифровки.
- Свободный пересказ модели не публикуется в Google/KB и не может соседствовать с H=`Нет`. В owner-only shadow он допустим только в памяти процесса до обезличенных метрик; production v3 его не сохраняет. Видимый конспект строится детерминированно по контракту §5.1.
- ТЗ-03 предполагает выполненный контракт ТЗ-01: фактический prompt сохраняет целые построчные реплики с `turn_id` и не склеивает их обратно в монолит. Без этого ТЗ-03 не включается.

## 4. Версия и контракт результата

Схема Analyse повышается до `analysis_schema_version=3`, prompt — до отдельной версии evidence-контракта.

```json
{
  "analysis_schema_version": 3,
  "prompt_contract_version": "analyse_v3_claim_evidence_1",
  "canonical_dialogue_sha256": "...",
  "analysis_input_sha256": "...",
  "structured_fields": {
    "next_step": {"action": "Отправить расписание", "due": null}
  },
  "history_summary": "Следующий шаг: отправить расписание.",
  "history_summary_meta": {
    "contract_version": "history_summary_v3_1",
    "parts": [
      {
        "template_id": "next_step_v1",
        "claim_ids": ["0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"],
        "turn_ids": ["T0042"],
        "source_code": "validated_claim"
      }
    ]
  },
  "claim_evidence": [
    {
      "claim_id": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "field_path": "structured_fields.next_step.action",
      "item_id": null,
      "raw_value": "Отправить расписание",
      "value_sha256": "...",
      "support_type": "explicit",
      "turn_refs": [
        {
          "turn_id": "T0042",
          "start_ms": 318400,
          "speaker_kind": "manager",
          "quote_text": "Я сегодня отправлю вам расписание в мессенджер.",
          "quote_sha256": "..."
        }
      ],
      "validation_status": "valid",
      "validation_errors": []
    }
  ]
}
```

Сырой JSON модели имеет ровно один корневой контракт; `additionalProperties=false` действует и на корень, и на каждый элемент:

```json
{
  "structured_fields": {"...": "строго по единой schema §5"},
  "claim_requests": [
    {
      "field_path": "structured_fields.next_step.action",
      "item_id": null,
      "support_type": "explicit",
      "turn_ids": ["T0042"]
    }
  ]
}
```

Оба корневых ключа обязательны. В `claim_requests[]` обязательны только `field_path`, `item_id`, `support_type`, `turn_ids`; `turn_ids` содержит от одного до трёх уникальных строк формата `Tdddd`. Любой иной корневой ключ, иной ключ claim, неизвестный путь/enum, неверный тип или пустая ссылка отклоняет ответ целиком до создания production payload. `analysis_schema_version`, hashes, `claim_id`, evidence и summary добавляет только сервис после валидации.

Модель возвращает только:

- значение в основном разрешённом поле анализа;
- `field_path` из закрытого списка;
- `item_id` для элемента списка;
- `support_type`;
- один–три `turn_id`, которые реально были в её prompt.

Ключ `history_summary` в сыром production-ответе v3 запрещён: итоговый конспект создаёт сервис только после валидации по §5.1.

Модель не присылает `claim_id` в любом виде и не присылает внутри claim `raw_value`, цитату, таймкод или speaker как источник истины. Эти ключи в сыром ответе отклоняются как лишние. Сервис сам создаёт `claim_id`, копирует `raw_value` из уже распарсенного основного значения `field_path`/`item_id`, а `quote_text`, `start_ms`, speaker и SHA — из канонического DialogueInput. Поэтому основное значение существует в одном месте, а модель не может подменить его другой копией внутри evidence.

`value_sha256` считается сервисом от канонического JSON фактического значения поля. Элемент списка получает отдельный `item_id`; нельзя одной общей ссылкой подтверждать весь массив значений.

`claim_id` не задаётся моделью окончательно и не является случайным: сервис детерминированно вычисляет его как SHA-256 от версии контракта, переносимого `call_key = stable_event_key(tenant_id, provider, provider_call_id)`, `field_path`, канонического item key и `value_sha256`. Локальный `id` и голый `source_call_id` без tenant/provider в формулу не входят. Модельный `item_id` — только локальный указатель в одном ответе. Сервис проверяет существование элемента, канонизирует его по схеме поля, удаляет точные дубли и записывает собственный item key, основанный на каноническом значении; порядок, придуманный моделью, в ID не входит. Одинаковый вход даёт тот же ID. Изменённое значение получает новый ID, а при переносе в Customer Timeline прежнее значение должно быть явно superseded, а не задублировано как одновременно действующее.

Закрытый enum `support_type`: `explicit` и `inferred`. Для любого high-risk поля допустим только `explicit`; неизвестное значение или `inferred` приводит к невалидному claim, а не к молчаливому преобразованию.

## 5. Поля, требующие доказательства

В schema v3 канонические пути для видимой бизнес-проекции фиксируются заранее, а не выбираются Google-публикатором эвристически. Старые дубли верхнего уровня (`summary`, `next_step`, `timeline`, `objections`, `target_product`, `lead_priority`) остаются только legacy-совместимостью и не являются источником v3/Google/KB.

| Канонический path | Тип/допустимые значения | Evidence/роль |
|---|---|---|

Неизвестные ключи/enum, неправильный тип, превышение лимита и любой legacy-путь отклоняются. Полная JSON Schema с `additionalProperties=false` генерируется из этой таблицы и является одним checked-in источником и для prompt validator, и для Analyse, и для Google tests; разработчик не поддерживает три ручные копии taxonomy.

Высокорисковые поля — всё, что может вызвать действие сотрудника, изменить клиентский профиль или оценку менеджера:

- результат разговора и статус договорённости;
- согласие, отказ, обязательство или обещание;
- факт оплаты, записи, покупки, переноса или отмены;
- возражение/причина отказа;
- следующий шаг, исполнитель и срок;
- сумма, бюджет, скидка и финансовое условие;
- класс, предмет, курс, продукт и формат;
- имена/контактные данные, если они извлечены из речи;
- претензия к менеджеру и поле «Что проверить РОПу»;
- любые поля, которые в будущем попадут в Customer Timeline как клиентский факт.

Для каждого непустого высокорискового значения требуется отдельный claim с `support_type=explicit` и минимум одной валидной ссылкой. Для list-поля каждый `item_id` требует собственный claim; неподтверждённый элемент удаляется поэлементно, а соседние подтверждённые элементы сохраняются. `inferred`, общий контекст и отсутствие возражения не считаются явным доказательством.

При отсутствии/ошибке доказательства:

- опубликованное высокорисковое поле становится `null`;
- `needs_review=true`, причина `claim_evidence_missing_or_invalid:<field_path>`;
- для элемента списка причина содержит `claim_evidence_missing_or_invalid:<field_path>[<item_id>]`;
- кандидат допустим только в оперативной памяти shadow-аудита и не сохраняется в production;
- автоматизация, Google, AMO и Timeline не имеют права восстанавливать его из summary или transcript.

### 5.1. Доказуемый конспект v3

В production v3 модель не возвращает свободный `history_summary`. После валидации claims сервис сам собирает его из версионированных шаблонов в фиксированном порядке:

1. техническая категория и безопасная нейтральная тема из закрытой таксономии;
2. продукт/предмет/формат/класс — только current valid claims;
3. результат и возражения — только current valid explicit claims;
4. следующий шаг и срок — только current valid explicit claims при trusted role guard;
5. фиксированное review-сообщение, если хотя бы один обязательный факт отброшен или роль не подтверждена.

Каждая смысловая шаблонная часть хранит собственный объект `history_summary_meta.parts[] = {template_id, claim_ids[], turn_ids[], source_code}`. Плоские общие массивы ссылок запрещены: они теряют соответствие части текста и доказательства. Нейтральная категория/тема без claim помечается отдельным закрытым `source_code` и не приписывается человеку. Порядок, пунктуация и формат шаблонов версионированы; одинаковые входы дают побайтно одинаковый summary и SHA. Нельзя добавлять в итог красивую фразу модели, если она не воспроизводится из разрешённых значений и claims.

Свободный draft модели, если он временно нужен для owner-only shadow-сравнения, существует только в памяти до обезличенной метрики и не попадает в `analysis_json`, Google, Timeline, логи или файлы. Для legacy v1/v2 старый собственный summary остаётся явно `legacy_not_checked`; его нельзя считать v3-доказательством.

## 6. Техническая валидация

После ответа модели сервис детерминированно проверяет:

1. `field_path` входит в версионированный allow-list и соответствует реально существующему значению.
2. `claim_id` уникален в пределах звонка; `item_id` соответствует одному элементу.
   Модельный `item_id`, не соответствующий существующему элементу текущего `field_path`, делает claim невалидным; до записи он заменяется каноническим item key сервиса.
3. Каждый `turn_id` существует в каноническом диалоге этого же переносимого `call_key`.
4. Реплика вошла именно в фактический сокращённый prompt, а не была отсечена.
5. `canonical_dialogue_sha256` и `analysis_input_sha256` совпадают с началом попытки.
6. `value_sha256` соответствует сохранённому значению.
7. Quote, timecode и speaker скопированы сервисом без смысловой обработки.
8. Для атрибутированного факта role guard ТЗ-02 имеет `trusted=true`.
9. Число/дата/класс/предмет имеют буквальный или утверждённый детерминированный якорь в указанной реплике. Смысловая нормализация выполняется только ТЗ-04.
10. Не больше трёх turn refs на claim; ссылки дублируются только если поля действительно разные.
11. Для закрытых категориальных полей — согласие/отказ, факт оплаты, запись/отмена/перенос, статус договорённости и тип возражения — отдельный детерминированный `contradiction_guard` проверяет явные маркеры полярности и отрицания. Реплика «не оплачивал» не подтверждает `structured_fields.result.status="payment_confirmed"`. «Оплачу», «хочу купить» и обсуждение суммы также не являются состоявшейся оплатой; доказанное согласие купить без факта оплаты даёт максимум `sale_agreed`. Только явная реплика о уже состоявшейся оплате может подтвердить `payment_confirmed`. При явном противоречии или неоднозначной области отрицания claim не становится valid и требует review. Guard использует версионированный закрытый набор правил и не объявляется полноценным пониманием языка.

При формировании prompt создаётся неизменяемый `attempt_context`: переносимый `call_key`, версии, все входные SHA, `role_guard_sha256`, точный упорядоченный `included_turn_ids` и его SHA. Это временное состояние конкретной попытки в памяти, а не новая таблица. Валидатор проверяет refs именно против этого списка и не запускает compression повторно после ответа. В финальной транзакции входные SHA пересчитываются из заново прочитанной строки; manifest успешной попытки записывается атомарно только вместе с анализом.

Технически валидная ссылка ещё не гарантирует правильную интерпретацию. Поэтому раздельно хранятся `validation_status`, `support_type` и `needs_review`.

## 7. Детерминированные факты

Если поле извлечено не моделью, а существующим regex/словарём, оно подчиняется тем же правилам:

- поиск выполняется по отдельным turns, а не по склеенному монолиту;
- сохраняется первый/точный `turn_id`, где найден якорь;
- значение и quote формирует сервис;
- отрицание, сомнение и роль проверяются до публикации;
- совпадение слова «цена» не означает возражение по цене, а «оплачу» не означает состоявшуюся оплату.

Детерминированные факты записываются в тот же массив `claim_evidence` с `support_type=explicit`; второй evidence-контракт не создаётся. `claim_id` считается по той же формуле, но версия источника берётся из отдельного `detector_contract_version`, который обязательно входит в analysis fingerprint.

Старое общее `evidence` переименовывается в `context_snippets` либо остаётся legacy-полем, но не считается доказательством claim.

## 8. Совместимость и миграция

- Старые v1/v2 продолжают читаться и не получают выдуманные ссылки задним числом.
- Для них `claim_evidence=[]`, причина `legacy_without_claim_evidence`.
- Они не считаются доказанными для новых автоматических действий/KB.
- Полноценное исправление возможно только повторным Analyse из сохранённых dialogue lines; повторный ASR не требуется.
- Массовый reset истории запрещён до готовности ТЗ-05. После всех пяти ТЗ история пересчитывается один раз партиями.

## 9. Защита от гонок

Основной анализ и `claim_evidence` сохраняются одной атомарной операцией. После LLM:

- начинается короткая SQLite write-транзакция;
- заново читаются строка, владелец lease, статус, `analysis_input_sha256`, `canonical_dialogue_sha256` и `role_guard_sha256`;
- любое расхождение отбрасывает весь ответ;
- нельзя сначала сохранить поле, а затем отдельным запросом дописать evidence;
- повторная попытка не смешивает claims двух запусков.

## 10. Обязательные тесты

1. Валидная ссылка на одно поле и отдельные ссылки для элементов списка.
2. Несуществующий, чужой и дублирующийся `turn_id`.
3. Ссылка на реплику, отсечённую из prompt.
4. Модель прислала выдуманную quote — поле игнорируется, quote строит сервис.
5. Изменение значения после вычисления `value_sha256`.
6. Неизвестный `field_path`, лишний JSON-ключ и превышение лимита refs.
7. Неподтверждённая роль очищает атрибутированный факт.
8. Отрицательное утверждение не получает фиктивное доказательство отсутствия.
9. Regex-класс/предмет получает точный turn ref; ложное совпадение отвергается.
10. Два похожих звонка никогда не смешивают ссылки.
11. Изменение диалога/роли между ответом и commit отклоняет результат.
12. Падение между ответом и транзакцией не оставляет частичный claim.
13. v1/v2 читаются без фабрикации evidence.
14. Длинный prompt сохраняет turn IDs выбранных целых реплик.
15. Логи/ошибки не содержат quote или полного prompt.
16. Частичный list: элемент без собственного claim не публикуется, соседний валидный элемент сохраняется.
17. Существующая противоположная реплика не подтверждает оплату/согласие/отказ; неоднозначное отрицание fail-closed.
18. Повторный Analyse того же входа создаёт те же `claim_id`; изменённое значение создаёт новый ID и явную связь supersession в KB-проекции.
19. Один параметризованный тест общей JSON Schema, Analyse validator и Google K projection проверяет три финансовых случая: намерение заплатить не даёт `payment_confirmed`; явная состоявшаяся оплата даёт `payment_confirmed`; согласие купить без оплаты даёт максимум `sale_agreed`.

## 11. Аудио- и бизнес-приёмка

1. Офлайн shadow без записи Google.
2. 50 confirmed-role звонков, затем 24 часа новых звонков строго в shadow: v3 не записывается в production `analysis_json`, не меняет статусы, не передаётся старому writer и не используется для действий; остаются только обезличенные метрики/хэши до общего cutover.
3. Слепая проверка 200 звонков двумя проверяющими: разные длительности, ASR-сходство, наличие обязательств, суммы/даты и качество ролей.
4. Для каждого claim проверяется и соответствие сохранённому transcript, и соответствие аудио.
5. Отдельно считаются причины review: отсутствие turn-структуры, отсутствие явной фразы, плохой ASR, неподтверждённая роль и ошибка модели. Нулевая публикация всех полей не считается успешным fail-closed результатом.
6. Для каждого поля измеряются: число вручную подтверждённых фактов в аудио, доля найденных valid claims, precision, доля review/null и изменение заполненности относительно старой выдачи. Старую заполненность нельзя считать эталоном точности.

GO:

- `100%` опубликованных непустых high-risk полей имеют валидную explicit-ссылку;
- `0` ссылок на другой звонок/отсечённую/несуществующую реплику;
- `0` неподтверждённых high-risk кандидатов экспортировано;
- не менее `95%` вручную проверенных ссылок действительно поддерживают заявленный факт;
- автоматически подтверждено не менее `70%` вручную размеченных явных high-risk фактов в целом и не менее `60%` по каждому критичному полю при наличии минимум 20 примеров этого поля; иначе требуется отдельный этап улучшения, а не формальный GO;
- не менее `90%` полезных high-risk полей старого анализа либо подтверждены, либо честно отправлены на review;
- рост null/review по каждому полю публикуется в отчёте; рост более чем на 30 процентных пунктов требует отдельного письменного бизнес-sign-off и не может быть скрыт общей метрикой;
- ни одной ложной оплаты, договорённости или даты в подтверждённом поле;
- p95 Analyse растёт не более чем на 20%, пропускная способность остаётся выше Whisper.

STOP:

- хотя бы одна межзвонковая ссылка;
- хотя бы один неподдержанный факт опубликован как подтверждённый;
- stale-worker сохранил claims;
- очередь Analyse устойчиво растёт;
- evidence используется как оправдание ошибки ASR без аудиопроверки.

## 12. Бизнес-эффект и ограничение

РОП сможет перейти от «модель так написала» к конкретной реплике и таймкоду. Это ускоряет проверку, предотвращает ложные задачи и делает качество измеримым для продажи продукта.

Наружное представление различает минимум три состояния: `verified`, `needs_review`, `legacy_not_checked`. Для Google существующая колонка «Нужна проверка» получает человекочитаемую причину и `[таймкод]`; для будущего интерфейса/API claim даёт access-controlled переход к этому месту аудио. Если безопасной ссылки на локальное аудио нет, показывается таймкод без публичного URL — нельзя раскрывать запись ради удобства.

Ограничение должно быть видимо заказчику: claim доказывает происхождение вывода из данного transcript, но не гарантирует, что ASR расслышал аудио правильно. Для денег, дат, имён и обязательств аудио остаётся окончательной проверкой при конфликте.

## 13. Что не делать

- не добавлять отдельную evidence-БД;
- не позволять модели авторить quote как источник истины;
- не считать первые три строки общим evidence;
- не отображать `context_snippets` в UI/экспорте как доказательство конкретного high-risk поля;
- не привязывать факт к реплике, которой не было в prompt;
- не мигрировать legacy evidence выдуманными ссылками;
- не отправлять quotes/ПДн в логи или аудит Claude;
- не включать Google/KB до ТЗ-05.

## 14. Журнал независимых аудитов Claude CLI

Максимум пять раундов; финальный GO требует отсутствия новых P0/P1.

### Раунд 1 — корневая гарантия и один источник истины

Claude CLI: `REVISE`.

Принято:

- `raw_value` больше не принимается от модели внутри claim, а копируется сервисом из единственного основного поля;
- точный `included_turn_ids` фиксируется в неизменяемом in-memory контексте попытки и используется для проверки ссылок без повторного запуска compression;
- `support_type` стал закрытым enum, high-risk принимает только `explicit`;
- построчный prompt с `turn_id` закреплён как обязательная предпосылка ТЗ-01, а причины ухода в review измеряются отдельно, чтобы GO не был пустым.

### Раунд 2 — смысловые противоречия и элементы списков

Claude CLI: `REVISE`.

Принято:

- добавлен узкий версионированный `contradiction_guard` для закрытых категориальных фактов; явное отрицание/противоречие не может стать valid evidence;
- каждый high-risk элемент списка требует собственного `item_id` и claim, неподтверждённые элементы удаляются по одному;
- `context_snippets` запрещено показывать как доказательство конкретного high-risk поля.

Уточнение:

- contradiction guard не выдаётся за полноценную семантическую модель: он ловит доказуемые прямые противоречия, а неоднозначность отправляет на review. Окончательная проверка качества остаётся аудио-аудитом.

### Раунд 3 — невырожденная бизнес-польза и traceability

Claude CLI: `REVISE`.

Принято:

- введены отдельные пороги automatic confirmed coverage по вручную размеченным аудио-фактам; пустая система больше не может формально пройти GO;
- наружное представление различает `verified`, `needs_review`, `legacy_not_checked`, показывает понятную причину и таймкод; аудиоссылка только с контролем доступа;
- `claim_id` стал детерминированным, изменение значения создаёт новый ID и требует supersession в Timeline.

Уточнение после спора:

- чистый null-rate относительно старой выдачи не принят как эталон качества: старые заполненные поля не имеют evidence. Он обязателен как прозрачная бизнес-метрика и при росте более 30 п.п. требует sign-off, но основной GO считается по вручную размеченным фактам из аудио.

### Раунд 4 — стабильные ID и единый evidence-контракт

Claude CLI: `REVISE`, новых P0 нет.

Принято:

- модельный `item_id` стал временным указателем, а стабильный item key вычисляет сервис из канонического существующего элемента; точные дубли удаляются до claims;
- несуществующий item делает claim невалидным;
- regex/словарные факты записываются в тот же `claim_evidence`, используют ту же формулу ID и отдельную версию детектора вместо создания второй схемы.

### Раунд 5 — финальная непротиворечивость JSON-контракта

Claude CLI: первоначально `STOP` из-за одного точного противоречия; замечание принято дословно.

Исправлено:

- `claim_id` удалён из сырого ответа модели; любой такой ключ отклоняется;
- окончательный `claim_id` создаёт только сервис по детерминированной формуле.

Claude в том же заключении явно подтвердил: после этой минимальной правки других незакрытых P0/P1 в ТЗ-03 не остаётся. Поэтому пост-аудитное состояние документа считается условным `GO`, без дополнительного шестого раунда и без выхода за согласованный максимум пяти проверок.

### После пяти раундов: перекрёстный аудит Codex

Это не шестой аудит Claude. После его пятого раунда текущий текст дополнен единой полной taxonomy schema v3, переносимым `call_key` в формуле claim ID и детерминированным `history_summary_v3`, собранным только из valid claims. Эти дополнения закрывают найденные на стыке ТЗ риски, но Claude их повторно не видел. Честный статус финального текста: `условный post-fix GO по Claude + отдельный перекрёстный аудит Codex`, а не безусловный Claude GO всей нынешней редакции.

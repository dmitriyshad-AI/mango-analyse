# Промпт для Codex + Claude CLI на MacBook M4

Ты работаешь над production-продуктом Mango Calls, но не имеешь права менять живой production на MacBook M1.

## 1. Получение кода

Репозиторий: `https://github.com/dmitriyshad-AI/mango-analyse.git`.

Исходная handoff-ветка: `codex/mango-calls-m4-handoff-20260816`.

Дмитрий отдельно передаст ожидаемый SHA этой ветки. До любой работы:

1. Выполни `git fetch --prune origin`.
2. Докажи, что `origin/codex/mango-calls-m4-handoff-20260816` существует и его SHA точно совпадает с переданным Дмитрием.
3. Убедись, что исходный clone/worktree чистый.
4. Создай новую ветку `codex/mango-calls-quality-v3-m4-20260816` и отдельный worktree. Не коммить напрямую в handoff-ветку и тем более в `main`.
5. Не переписывай историю, не force-push и не удаляй ветки/теги.

Если SHA, ветка или чистота не доказаны — STOP и отчёт Дмитрию.

## 3. Жёсткие границы

- Не подключайся к Mango API, рабочей Google-таблице, production SQLite, Customer Timeline, AMO, Tallanto и сервисам M1.
- Не запускай и не меняй `launchd` на M1.
- Не используй production credentials и не проси их для разработки.
- Не публикуй ПДн, тексты разговоров, телефоны, ФИО, ключи, токены и абсолютные пути из конфиденциального пакета.
- Конфиденциальный пакет Яндекс.Диска, если Дмитрий его предоставит, сначала скопируй в локальный owner-only каталог вне Git/облака, проверь SHA объекта, открой read-only и не коммить его содержимое.
- Raw audio, raw transcript, оба ASR-варианта и их evidence неизменяемы.
- Google остаётся витриной, не базой знаний и не источником идентичности.
- M1 остаётся единственным live-writer. Не проектируй двустороннюю синхронизацию SQLite.

Офлайн-пакет без пароля доступен в личном Яндекс.Диске владельца по относительному пути:

`Mango Analyse/M4 Handoffs/2026-08-16/mango_calls_m4_confidential_handoff_20260816.dmg`

Ожидаемый SHA-256 указан в соседнем файле с суффиксом `.dmg.sha256` и отдельно в сообщении Дмитрия. Сначала сверь оба значения и фактический SHA в каталоге Яндекс.Диска, затем скопируй DMG в локальный owner-only каталог вне облака и Git. Пароль не требуется. Открывай только read-only; после открытия проверь все SHA из `MANIFEST.md` и `PRAGMA quick_check=ok`. Любое несовпадение — STOP.

## 4. Сначала повторный аудит

До реализации:

1. Сопоставь каждое требование ТЗ с существующим кодом и тестами.
2. Отметь `уже реализовано / частично / отсутствует / противоречие`.
3. Запусти базовый test suite правильным `PYTHONPATH` и сохрани точную команду/результат.
4. Проверь, что новый Google publisher уже содержит ledger, reservation/recovery, exact readback, МСК, `N мин M с`, newest-first, J-height и P-clip. Это не переписывать.
5. Проверь два свежих P0: нейтральные роли вида `Спикер ...` не должны тихо теряться; любая непубликованная строка должна создавать структурированный инцидент и заметный статус, не блокируя доказанно валидные строки.

Привлеки Claude CLI Opus с максимальной глубиной как независимого аудитора. Claude работает read-only и не заменяет тесты.

## 5. Реализация: обязательный порядок

### Этап A — транспортные P0

1. Исправь публикацию корректных neutral-speaker/mono/complex-topology звонков без угадывания ролей.
2. Сделай silent skip невозможным: структурированный incident, ненулевой/явный health status и regression tests.
3. Подготовь versioned `launchd`-шаблон для прямого запуска уже существующего publisher вместо Codex automation, но ничего не устанавливай и не переключай на M1.
4. Добавь точный учёт токенов Analyse.
5. Добавь конфигурационный способ отключить LLM-ветку Resolve; включать его можно только после exact-hash regression всех сохранённых случаев, где ветка вызывалась.

### Этап B — пять ТЗ качества

1. ТЗ-01: Analyse получает канонический хронологический диалог с `turn_id` и таймкодами.
2. ТЗ-02: неподтверждённые роли закрывают role-dependent факты и требуют review.
3. ТЗ-03: каждый high-risk факт ссылается на существующий `turn_id`; exact quote строит сервис, а не модель.
4. ТЗ-04: raw не переписывается; нормализованные значения и МСК живут отдельно с версиями правил.
5. ТЗ-05: интегрируй новый Analyse с уже существующим publisher через version/hash/stale-refresh. Не создавай второй publisher или вторую call DB.

После каждого ТЗ выполни до пяти последовательных независимых аудитов Claude CLI. Каждое замечание либо исправь, либо отклони с воспроизводимым доказательством. Не начинай массовый исторический перерасчёт.

### Этап C — эксплуатационная готовность в коде

1. Добавь read-only полноту Capture: provider totals/window/cursor и явный отчёт gaps без повторного скачивания.
2. Добавь наблюдаемость очередей, age/SLA, heartbeat, dead-letter и понятные коды причин.
3. Подготовь безопасный workflow ручной проверки.
4. Подготовь sealed snapshot/manifest/restore runbook и схему одноразового crosswalk M4 history → M1 canonical archive. Ничего не импортируй в production.

## 6. Проверки качества

- Unit и integration tests для каждого контракта.
- Crash/retry/lease/idempotency tests.
- Тесты на unknown role, neutral speaker, mono, malformed dialogue и конфликт ASR.
- Тесты UTC → Europe/Moscow, перехода даты, денег, сроков, класса, предмета и бренда.
- Тесты `fact → turn_id → exact quote → input SHA`.
- Тесты stale Google projection без реального обращения к Google.
- Повторный прогон даёт ноль дублей и ноль лишних модельных вызовов.
- Secret scan всего diff и новых файлов.
- `git diff --check`, полный применимый test suite и чистый worktree.

Для смены модели/промпта подготовь слепой корпус 150–200 обезличенных случаев и A/B-метрики. GigaAM v3 CTC, третий ASR и два GigaAM worker не включать.

## 7. Что вернуть Дмитрию

1. Название ветки и точный commit SHA.
2. Краткий список изменений простыми словами.
3. Таблицу `требование → файл/строка → тест → результат`.
4. Полные команды тестов и счётчики passed/failed/skipped.
5. Secret-scan report.
6. Отчёт всех раундов Claude: замечание, принято/отклонено, доказательство.
7. Список миграций и порядок отката.
8. Отдельный список того, что сознательно не реализовано и почему.
9. Подтверждение: production M1, Google, Mango API, рабочие SQLite и службы не изменялись.

Запушь только новую ветку. Не создавай PR и не сливай её в `main` без отдельного разрешения Дмитрия. После этого остановись и передай результат для независимой проверки на M1.

# M1: довести Customer Timeline до чистой интеграции и доказанной пользы менеджеру

## 0. Простое объяснение для Дмитрия

M1 уже построил полезную офлайн-базу: деньги и сделки сходятся, чужих данных в проверенной сотне нет, 96 из 100 карточек содержат полезную историю. Но принять всю ветку нельзя: она смешала ядро Timeline, live-контур, публикацию и служебные отчёты; добавила 53 падения полного набора тестов; база собрана не последним кодом; настоящая цепочка до текста заметки AMO не проверена.

Эта задача не строит новую Timeline. Она должна:

1. Сначала показать 10 настоящих черновиков менеджеру без записи в AMO.
2. Перенести только полезное ядро Timeline в чистую ветку от свежего `main`.
3. Починить доказанные дефекты и получить ноль новых падений.
4. Пересобрать базу одним кодом и доказать повтор без дублей.
5. Отдать отдельные, не включённые пакеты live и publish.
6. Найти крупную уборку, но не задерживать ею полезный результат.

## 0.1. Образ результата и владельцы

После задачи существует одна чистая ветка-кандидат от зафиксированного актуального
`main`, в которой менеджер по 10 реальным клиентам получает точный, полезный и
проверяемый черновик из Customer Timeline: без чужих данных, с подтверждёнными
источниками и с конкретным следующим шагом либо явной причиной бездействия.
Та же версия кода дважды собирает одну staging-базу без дублей и новых бизнес-строк
на неизменных входах. По S100 каждый неактивный статус объяснён: `closed` не требует
действия, `empty` имеет причину/источник обогащения, `review` имеет владельца,
действие и срок.

M1 делает трёхдеревную сверку, собирает чистую ветку-кандидат и проводит S10/S100.

решений и тестов, а не родителем автоматического merge. M1 не сливает `main`, не
публикует snapshot и не включает live-контур.

## 2. Фаза 0 — продуктовый экзамен до большого слияния

Выбрать 10 реальных клиентов, у которых одновременно есть exact AMO identity, полезная Timeline-история и активная сделка либо подтверждённая оплата за последние 90 дней.

Выполнить настоящий путь без внешней записи на временном S10/source worktree:

`exact AMO lookup -> Timeline context -> SubscriptionLlmDraftProvider.build_draft() -> перехваченная AMO note`

Для каждого клиента сохранить обезличенно:

- какие источники нашлись;
- фактический текст контекста модели;
- фактический текст черновика;
- следующий шаг либо код причины бездействия;
- активную сделку и подтверждённые оплаты за 90 дней;
- время выполнения.

Обязательные отрицательные контроли:

1. Подменить exact lookup на другого клиента: чужие данные не попадают, путь закрывается либо результат меняется.
2. Вернуть `None`: нельзя незаметно использовать offline-ID как якобы live AMO route.
3. Monkeypatch-ом удалить один подтверждённый источник клиента: он обязан исчезнуть из контекста и provenance. Текст обязан измениться только если этот источник был единственным основанием соответствующего утверждения или следующего шага.
4. Перехватить все AMO POST/PUT/PATCH: фактических внешних записей ноль.

Приёмка Фазы 0:

- `10/10` exact AMO route;
- `0/10` чужих клиентов;
- `10/10` черновиков содержат прямой ответ или честную причину бездействия;
- независимые GPT breaker, GPT business reviewer, Claude Sonnet breaker и Claude Fable business reviewer видят фактические тексты, а не рассказ исполнителя;
- минимум `8/10` признаны полезными без существенной переписи. Если меньше — STOP: сначала исправить общий класс, повторить S10 и только потом интегрировать ядро.

## 4. Исправить подтверждённые дефекты

### 4.1 Core

1. Canonical import: не подгонять код под число вложенных `bulk_write`. Доказать один физический commit/rollback и атомарность. Исправить измеритель либо минимально убрать лишний context только если savepoint-контракт сохраняется.

3. Старая почта без первичного timestamp может быть историей, но не определяет свежесть и следующий шаг. Посчитать объём и влияние отдельным балансом. Не ссылаться на несуществующий ID решения; если правила ещё нет в каноне, оформить предложение владельцу, а не самовольно создавать решение.

## 7. S100 — бизнес-приёмка

Сохранить фактический обезличенный формат, который увидит менеджер. Отдельно показать текущие категории, не маскируя общим PASS: `21 active / 38 review / 28 empty / 13 closed` или новые фактические числа.

Для каждого `review` обязательны владелец, конкретное действие и срок. Для `empty` — источник обогащения либо явное исключение из рабочей очереди. Технический код без понятного менеджеру текста не считается готовым.

Независимые GPT и Claude бизнес-аудиторы проверяют 100 текстов. Технический знаменатель — все 100, категории не исчезают. Бизнес-знаменатель — клиенты `active + review`; результат считается manager-ready, если есть конкретный следующий шаг либо review-задача с владельцем, действием и сроком. Приёмка: минимум 80% бизнес-знаменателя manager-ready; отдельно не менее 80% фактических сгенерированных draft-текстов полезны без существенной переписи; 0 чужих клиентов; 0 выдуманных фактов; 0 пропущенных P0; 0 скрытых потерь из закрытых балансов. `closed` и `empty` не улучшают процент и показываются отдельно.

Нулевые показатели подтверждать не голосованием моделей, а сверкой provenance с исходными строками и canary-мутациями. Модели оценивают смысл и пользу; расхождения разрешает главный Codex по сырью.

## 10. Итоговый критерий

Core принимается только если Фаза 0 прошла, у полного suite нет новых падений, SQLite собрана тем же SHA, повтор идемпотентен, все балансы закрыты, S100 прошла смысловую проверку, внешних write-операций нет, а Git-кандидат не содержит live/publish включение и служебный мусор.

Будущий 10-дневный пилот не входит в эту задачу. Его окно начинается только после отдельного решения Дмитрия, непустого allowlist из 1–3 manager/channel пар и проверки `live_truth.py`. При пустом allowlist пилот не считается начавшимся.

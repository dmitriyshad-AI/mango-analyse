# ТЗ-04. Безопасная нормализация брендов, фактов и времени МСК

Статус: проект, реализация запрещена до отдельного подтверждения Дмитрия.

Зависимость: применима к бизнес-фактам только после valid claims ТЗ-03. Raw transcript и evidence неизменяемы.

## 1. Простыми словами

Полную расшифровку нельзя переписывать задним числом: это исходный материал. Но в отдельных бизнес-полях можно показывать нормальное название бренда, предмета, класса, даты или суммы — только когда исправление однозначно и видно, по какому правилу оно сделано.

Пример: в реплике остаётся «УНПК МФТИШ», а рядом бизнес-поле получает `УНПК МФТИ`, правило `known_alias`, ссылку на реплику и отметку deterministic. Если система не уверена, она ничего не угадывает.

Время звонка хранится в UTC, а пользователю показывается в МСК ровно один раз. В конспект время вообще не вставляется: оно уже есть в отдельной колонке.

## 2. Доказательства

- Готовый нормализатор уже есть: `src/mango_mvp/quality/tenant_text_normalizer.py`; он содержит проверенные варианты брендов/продуктов и frozen corpus `tests/fixtures/tenant_text_normalizer_frozen_corpus.jsonl`.
- Analyse этот нормализатор в production-пути звонок → Google сейчас не использует.
- `_format_started_at()` в `src/mango_mvp/services/analyze.py:590-596` вызывает системный `astimezone()` только для aware datetime; naive значение оставляет как есть.
- SQLite хранит naive UTC. На read-only срезе `1 705/1 705` history summaries содержали точное UTC-время, `0/1 705` — МСК `+3`.
- `_compose_history_summary()` в `analyze.py:1513-1528` всегда добавляет время и менеджера, хотя prompt требует конспект без такой преамбулы, а Google уже имеет отдельные колонки даты/менеджера.
- Живая Google-автоматизация уже правильно переводит UTC → МСК и форматирует длительность/строки. Это поведение нужно перенести в проверяемый код ТЗ-05, а не создавать вторую трактовку.

## 3. Единый контракт данных

Неизменяемые источники:

- audio и его manifest/SHA;
- `transcript_text`, `transcript_variants_json.dialogue_lines`;
- raw quote в `claim_evidence`;
- исходный `started_at` в UTC;
- сырые ответы ASR/Resolve.

Нормализованное значение хранится отдельно в `analysis_json.normalized_facts`:

```json
{
  "field_path": "structured_fields.student.school",
  "raw_value": "УНПК МФТИШ",
  "normalized_value": "УНПК МФТИ",
  "claim_id": "...",
  "rule_id": "brand.unpk_mfti.known_alias",
  "engine_version": "tenant_text_engine_v1",
  "ruleset_version": "tenant_ru_v1",
  "tenant_id": "mango",
  "status": "normalized_deterministic"
}
```

Каждая замена обязана иметь raw, normalized, valid `claim_id`, неизменяемый `rule_id`, версию правил и tenant. Нормализация идемпотентна: повторный запуск тех же версий даёт тот же JSON/SHA.

`field_path` берётся только из закрытой claim taxonomy ТЗ-03; нормализатор не вводит собственные пути. `tenant_id` берётся из обязательной настройки службы `calls_tenant_id`, фиксируется в analysis fingerprint и для текущего production явно равен `mango`. Неявный default и использование controlled-call tenant запрещены: при отсутствующей/невалидной настройке tenant-specific нормализация fail-closed отключается.

Источник истины — raw claim + rule provenance. `normalized_value` не заменяет evidence и не используется для изменения transcript.

## 4. Что переиспользовать

- существующий `tenant_text_normalizer.py` и его frozen corpus;
- текущие `SUBJECT_PATTERNS`/утверждённые справочники только после объединения в один tenant-scoped ruleset;
- `ZoneInfo("Europe/Moscow")` из стандартной библиотеки;
- claims/turn refs ТЗ-03;
- один общий fingerprint versions для Analyse и Google.

Нельзя создавать второй независимый словарь брендов или запускать LLM для «исправления на слух».

Read-only аудит подтвердил: текущие функции normalizer возвращают строку и не сообщают `rule_id`/version. Будущая реализация включает точечное расширение того же модуля: новый provenance-result с обязательным tenant поверх существующих compiled patterns. До изменения проводится аудит всех caller'ов. Старые string-return wrappers сохраняют побайтно прежнее замороженное поведение только для явно перечисленных legacy caller'ов и не используются новым Analyse/Google-путём; они не получают скрытый default tenant. Создавать второй набор regex запрещено, а legacy caller'ы затем мигрируются отдельно.

## 5. Разрешённые автоматические действия

Только закрытые детерминированные правила с положительными и отрицательными тестами:

- известные точные алиасы брендов/организаций;
- утверждённые алиасы предметов и форматов;
- класс 1–11 при явном контексте обучения;
- однозначное числовое представление суммы без смены смыслового типа;
- абсолютная дата с однозначными днём/месяцем/годом;
- относительное `сегодня/завтра` от даты звонка в МСК, если говорящий/claim доверен;
- Unicode, пробелы и типографика только в display/business-копии.

## 6. Запрещённые догадки

- fuzzy-замена неизвестной организации на ближайший бренд;
- ФИО по похожему звучанию;
- «МПК/НПК/УНПК» без exact approved alias;
- «цена упоминалась» → `price_sensitivity=high`;
- вопрос о скидке → согласованная скидка;
- намерение оплатить → оплата состоялась;
- «в семь» → время или класс без контекста;
- «на следующей неделе»/неоднозначный понедельник → точная дата;
- выбор одного значения при конфликте ASR A/B или evidence;
- автоматическая смена speaker/роли.

При сомнении: `normalized_value=null`, raw сохраняется в claim, `needs_review=true`, причина с field/rule family.

## 7. Контракт времени

Внутренний источник: UTC. Отображение: `Europe/Moscow`.

```python
if value.tzinfo is None:
    utc_dt = value.replace(tzinfo=timezone.utc)
else:
    utc_dt = value.astimezone(timezone.utc)
msk_dt = utc_dt.astimezone(ZoneInfo("Europe/Moscow"))
```

Правила:

1. Naive datetime из действующей SQLite трактуется как UTC по доказанному capture-контракту.
2. Конвертация выполняется в одном общем formatter ровно один раз.
3. В UTC-данных не записывается сдвинутое МСК-время.
4. `history_summary`/«Конспект разговора» больше не содержат автоматически добавленную дату и имя менеджера; они находятся в отдельных колонках/metadata.
5. Relative due рассчитывается от `.date()` результата того же общего московского formatter, только при valid claim и однозначной фразе. Отдельная конвертация UTC→МСК для due запрещена.
6. Версия timezone contract входит в Analyse/Google fingerprint.
7. В рамках ТЗ-04 конкретно исправляются `analyze.py:590-596` и `1513-1528`: общий formatter правильно трактует naive UTC, а дата/менеджер удаляются из summary. В ТЗ-05 этот уже готовый formatter переиспользуется Google-публикатором; второй timezone-алгоритм там не создаётся.

## 8. Конфликты и версии

- При A/B ASR disagreement по числу, дате, бренду, классу или предмету автоматическая нормализация запрещена до явного выбранного доказательства.
- Для scalar `field_path` более одного valid claim с разным `raw_value` всегда означает `field_conflict:multiple_valid_claims`: выбор по порядку/ID/confidence запрещён, normalized value остаётся null и требуется review. Для list-field разные канонические элементы допустимы, но конфликт двух raw-значений для одного item key блокирует только этот элемент.
- Изменение ruleset не переписывает старый результат молча: новый fingerprint делает его stale для управляемого повторного Analyse/Google refresh.
- Fingerprint нормализации включает `engine_version`, `ruleset_version`, `tenant_id`, claim taxonomy/detector version и `timezone_contract_version`. Любое изменение compiled patterns, приоритетов/matching-логики, словаря, tenant или времени требует version bump и делает старый normalized result stale.
- Изменение, supersession или инвалидация `claim_id`, на который ссылается normalized fact, также меняет fingerprint и делает нормализацию stale; ссылка на исчезнувший claim не может оставаться valid.
- Правило добавляется только вместе с frozen positive/negative fixtures, владельцем, причиной и версией.
- Каждый bump `ruleset_version`, а не только первый запуск, проходит shadow diff на истории, ручную проверку всех changed rows (при количестве >200 — детерминированную стратифицированную выборку 200 плюс все high-risk изменения), не менее 100 неизменённых отрицательных примеров и отдельную канарейку. Версия не становится active только потому, что unit-тесты зелёные.
- Tenant-specific алиасы не становятся глобальными для другого заказчика. Общий engine один, набор правил — по tenant.
- Удалённое/изменённое правило сохраняет provenance старого результата; история не теряет объяснимость.

## 9. Безопасность Google-значений

Формульная защита окончательно выполняется публикатором ТЗ-05 для всех текстовых колонок. Любая строка, начинающаяся на `=`, `+`, `-` или `@`, передаётся как текст, а не как формула. Нормализатор не должен обходить эту защиту.

## 10. Тесты

1. Raw transcript/dialogue/evidence до и после имеют тот же SHA-256.
2. Известный alias нормализуется с rule/version/claim.
3. Неизвестный похожий бренд не меняется.
4. Frozen positive/negative corpus, ноль ложных замен в утверждённом negative corpus.
5. Class/subject/format: положительные контекстные и ложные совпадения.
6. Цена ≠ бюджет/возражение; скидка ≠ согласование; намерение ≠ оплата.
7. UTC naive → МСК, aware UTC, aware MSK, границы суток/года.
8. Повторный formatter не добавляет `+3` второй раз.
9. Summary не содержит дата/менеджер-преамбулу.
10. Relative due от `.date()` общего МСК-formatter, включая звонок поздно вечером UTC с переходом на следующие московские сутки; неоднозначное выражение остаётся без даты.
11. A/B conflict блокирует автоматическую нормализацию.
12. Повторный запуск идемпотентен.
13. Tenant A alias не применяется tenant B.
14. Formula-like text остаётся текстом в projection.
15. Изменение ruleset или referenced claim меняет fingerprint/stale state, но не raw.

## 11. Rollout и приёмка

1. Shadow diff без записи SQLite/Google.
2. Ручная проверка changed rows по правилу выше и не менее 100 стратифицированных неизменённых строк. Дмитрий или письменно назначенный им владелец утверждает чек-лист: rule/version, выборка, false positives/negatives, решение GO/STOP и дату.
3. Канарейка 50 новых звонков, затем 200: бренды, предметы, классы, числа, даты, A/B conflicts. До общего cutover она строго shadow: не пишет production `analysis_json`/статусы/Google и не передаёт новую проекцию старому writer; сохраняются только обезличенные метрики/хэши.
4. История не пересчитывается до ТЗ-05.
5. Для каждого следующего ruleset: shadow gate, затем первые 20 реальных срабатываний нового/изменённого правила под автопаузой при первой ложной замене.
6. После GO агрегаты `normalized/unchanged/review/error` по tenant/rule проверяются еженедельно восемь недель, затем ежемесячно; без текстов, телефонов и ПДн. Необъяснимый скачок частоты/ошибок останавливает только затронутое правило.

GO:

- `0` изменений raw transcript/evidence;
- `0` ложных замен на утверждённом negative corpus и аудио-выборке;
- `100%` нормализованных high-risk фактов имеют valid claim/rule/version;
- `100%` дат звонка отображаются по одному `Europe/Moscow` contract;
- `0` конспектов с автоматически вставленной UTC/manager-преамбулой;
- повторный запуск даёт тот же SHA;
- false-positive на 200-звонковой аудиопроверке — `0` для денег, дат, класса, бренда и оплаты.

STOP:

- изменился raw источник;
- хотя бы одна догадка/fuzzy-замена прошла автоматически;
- двойной timezone shift;
- конфликт A/B был скрыт одной нормализованной версией;
- tenant-specific правило протекло другому заказчику.

## 12. Бизнес-эффект

Таблица станет удобнее: одинаковые бренды/предметы группируются одинаково, время соответствует Москве, а числа и даты не «исправляются» наугад. Для продажи продукта особенно важно, что каждое исправление объяснимо и tenant-scoped.

## 13. Что не делать

- не переписывать полный transcript;
- не создавать второй normalizer/справочник;
- не использовать LLM/fuzzy для автозамены;
- не хардкодить `+3` вместо `ZoneInfo`;
- не встраивать дату/менеджера обратно в summary;
- не запускать массовый backfill до ТЗ-05.

## 14. Журнал независимых аудитов Claude CLI

Максимум пять раундов; финальный GO требует отсутствия новых P0/P1.

### Раунд 1 — границы, tenant и переиспользование

Claude CLI: `REVISE`, новых P0 нет.

Принято:

- разделены зоны: Analyse/time/summary исправляются в ТЗ-04, Google только переиспользует тот же formatter в ТЗ-05;
- подтверждён реальный API normalizer: provenance отсутствует, поэтому точечное обратно совместимое расширение включено в scope без второго словаря;
- `tenant_id` стал обязательной явной service-настройкой и частью fingerprint;
- `field_path` ограничен единой taxonomy ТЗ-03.

### Раунд 2 — конфликты claims и единая календарная дата

Claude CLI: `REVISE`.

Принято:

- для scalar-поля два разных valid claims теперь всегда создают явный конфликт без выбора по порядку; для list-полей конфликт определяется на уровне item key;
- изменение/инвалидация referenced claim делает normalized fact stale;
- relative due берёт `.date()` только из общего московского formatter, включая переход суток.

### Раунд 3 — жизненный цикл словарей

Claude CLI: `REVISE`.

Принято:

- каждый bump ruleset проходит shadow, ручную changed/unchanged проверку и собственную канарейку, а не активируется только по unit-тестам;
- утверждён явный владелец и письменный протокол приёмки;
- введён лёгкий контроль дрейфа по tenant/rule после GO без хранения текстов/ПДн.

### Раунд 4 — версия движка и legacy-совместимость

Claude CLI: `REVISE`, новых P0 нет.

Принято:

- provenance и fingerprint теперь включают отдельный `engine_version`, который меняется при правке regex/matching-логики;
- старый string API не получает скрытый tenant: его текущие caller'ы сначала инвентаризируются, wrappers сохраняют только замороженное прежнее поведение и запрещены в новом Analyse/Google-пути;
- новый provenance API всегда требует явный tenant и переиспользует те же patterns без второго словаря.

### Раунд 5 — финальный независимый аудит

Claude CLI: `GO`.

Новых P0/P1 не найдено. Подтверждены неизменяемая raw-граница, tenant isolation, fail-closed конфликты, единый московский formatter, жизненный цикл каждого ruleset, отдельная версия engine и безопасная legacy-совместимость.

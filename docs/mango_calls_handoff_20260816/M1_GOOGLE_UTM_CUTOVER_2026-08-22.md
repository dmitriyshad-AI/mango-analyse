# Перенос таблицы звонков на 18 столбцов

## Что изменено

Первые 16 столбцов остаются в прежнем порядке и с прежним содержанием:

1. №
2. Дата и время (МСК)
3. Менеджер
4. Направление
5. Длительность
6. Категория
7. Телефон клиента
8. Нужна проверка
9. Тема
10. Конспект разговора
11. Результат
12. Возражение / причина
13. Следующий шаг
14. Срок
15. Что проверить РОПу
16. Полная расшифровка

Добавлены:

17. Основание ключевых выводов
18. UTM и страница заявки

Столбец 18 содержит UTM выбранной заявки и явно показывает основание связи:
прямой `lead_id` из записи звонка либо **предполагаемое** косвенное правило
«точный телефон и ближайшая предыдущая заявка». Косвенная связь не называется
доказанной; для неё показывается временной разрыв.
Далее выводятся:
`utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`,
`utm_referrer` и точную строку `url:` из обычной заметки заявки. Если связь
неоднозначна, вместо догадки выводится понятная причина. UTM-поля AMO не имеют
истории изменений, поэтому в каждой строке явно указано: это снимок карточки
при первом сопоставлении, а не доказанные значения на момент звонка. Строка `url:` остаётся
исторически ограниченной временем создания заметки.

## Как выбирается заявка

1. Если в записи звонка есть корректный прямой `amocrm_lead_id`, используется
   именно эта заявка. Она всё равно не может быть создана после звонка, а
   телефон звонка должен быть найден ровно в одном из её связанных контактов.
2. Без прямой связи контакт ищется по полному нормализованному телефону.
3. Если точных контактов несколько, UTM не подставляются.
4. Среди заявок контакта выбирается ближайшая заявка, созданная не позже
   звонка.
5. Будущая заявка не подходит. Заявка старше 30 дней без прямой связи со
   звонком также не подходит.
6. Сначала выбирается заявка, и только потом проверяется наличие UTM. Нельзя
   взять более старую заявку только потому, что в ней заполнены метки.
7. Страница заявки берётся только из отдельной строки `url:` обычной заметки,
   созданной не позже звонка. Несколько разных прошлых URL считаются
   неоднозначностью. Поле `REFERRER` страницей заявки не считается.

Сопоставление работает только для ограниченной партии издателя: не больше 25
звонков за запуск. Уже подтверждённый блок сохраняется в защищённом локальном
состоянии службы и повторно из AMO не запрашивается.

Кэш автоматически перестаёт подходить, если в базе исправились телефон, время
звонка или прямой `lead_id`; такие случаи считаются `changed`. Изменение только
карточки AMO после первого сопоставления автоматически не обнаруживается.
Редактировать JSON состояния вручную запрещено: связанные карты кэша должны
меняться согласованно. Точечное принудительное обновление таких строк требует
отдельного безопасного инструмента и не входит в это переключение.

## Обязательная настройка M1

В защищённый файл конфигурации издателя добавить путь:

```json
"schema_version": "mango_calls_live_google_config_v2",
"amo_read_env": "/Users/dmitriy/.mango_secrets/foton_crm_readonly_mcp_connector.env"
```

Файл должен принадлежать владельцу службы и иметь права `0600`. Доступ должен
быть только на чтение. Код не выполняет запись в AMO.

## Безопасное переключение

Текущую рабочую вкладку не перестраивать на месте. Она остаётся быстрым
откатом вместе со старой конфигурацией и старой проверенной версией кода.
Новый код намеренно не принимает старую схему заголовков: для отката нельзя
направлять его на 16-столбцовую вкладку.

1. Создать отдельную вкладку, например `Звонки v3`, с точными 18 заголовками
   выше. Столбцы `S:Y` оставить пустыми: издатель временно использует их только
   внутри одного запроса для сортировки и сразу очищает. До первого shadow
   вручную выставить столбцам J, Q и R одинаковую ширину, точно равную
   `summary_width_px` из новой конфигурации. Иначе штатная read-only проверка
   макета обязана остановиться до bootstrap.
2. Создать для новой вкладки отдельный защищённый файл состояния. Старое
   состояние не переносить и не перезаписывать.
3. Указать в копии конфигурации новые `sheet_id`, `sheet_title`, новый путь
   `state`, `amo_read_env` и точный SHA проверенного кода.
4. Выполнить теневую проверку без `--execute`. Внешней записи быть не должно.
   В отчёте `utm_enrichment.skipped` должен быть равен нулю, а сумма
   `received + reused` — числу `selected`. Число запросов AMO должно быть
   ограничено выбранной партией. Повторная проверка на неизменных данных
   должна переиспользовать локальный результат без новых запросов AMO.
   Отдельно зафиксировать `attributed`, `probable` и `unattributed`: прямая
   связь, предполагаемая связь по телефону/времени и отсутствие связи не
   смешиваются в один зелёный счётчик.
5. Выполнить штатную инициализацию пустой вкладки с отдельным подтверждением.
6. Опубликовать последовательно 1, затем 10, затем не больше 25 звонков. После
   каждой партии проверить чтением обратно точное число строк и все 18 полей.
7. РОП вручную проверяет минимум 10 строк из `attributed` и все причины из
   `probable`/`unattributed`: телефон, время звонка, основание связи, выбранную
   заявку, метки и страницу.
8. После суток без расхождений переключить штатную публикацию на новую
   конфигурацию. Старую вкладку не удалять до отдельного решения Дмитрия.

## Условия остановки

Переключение запрещено, если:

- заголовки отличаются хотя бы в одном из первых 18 столбцов;
- в `S:Y` есть пользовательские данные;
- по точному телефону найдено больше одного контакта AMO;
- выбрана заявка после звонка или старше допустимого срока;
- изменился вызов, выбранный ограниченной партией, после добавления UTM;
- чтение Google после записи не совпало с отправленными 18 полями;
- код, конфигурация или рабочая папка не совпадают с проверенным SHA.

## Что эта задача не делает

- не меняет текущую рабочую Google-таблицу;
- не пишет в AMO;
- не запускает ASR, Resolve или Analyze;
- не меняет рабочую базу звонков;
- не включает службу автоматически.

Включение на M1 является отдельным управляемым действием после приёмки кода и
проверки новой вкладки.

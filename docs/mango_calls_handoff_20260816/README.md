## Итог простыми словами

Сейчас распознавание и конвейер работают, но «умный вывод» над звонком недостаточно доказуем:

1. Правильные реплики уже существуют, но Analyse часто получает два больших блока каналов и теряет порядок вопрос–ответ.
2. Примерно в семи звонках из десяти роли менеджера и клиента не подтверждены, но система всё равно может сформировать обещание или следующий шаг.
3. Ни один проверенный Analyse не хранит доказательство конкретного бизнес-факта.
4. В конспект системно попадало UTC-время вместо МСК; словари брендов существуют, но не встроены в доказательный production-путь.
5. Google иногда сохраняет старую версию собственного конспекта: `sync_status=done` не доказывает актуальность строки.

Правильная последовательность:

```text
Сохранённые хронологические реплики
  → запрет угадывать роли
  → ссылка каждого важного факта на реплику/таймкод
  → безопасная нормализация и МСК
  → один проверяемый Google-публикатор
  → после приёмки — Customer Timeline / база знаний
```

## Пять ТЗ

### 1. [Канонический диалог для Analyse](./TZ-01-canonical-dialogue-input.md)

Не распознаём заново. Analyse читает уже готовые `dialogue_lines` в хронологическом порядке, с `turn_id` и таймкодами. Длинный разговор сокращается только целыми репликами. Вход и владелец lease проверяются атомарно перед записью результата.

Доказательство на снимке 15.08.2026 02:48:18 МСК: у `1 833/1 843` готовых Analyse были непустые dialogue lines, но `1 275` входов начинались с `CHANNEL_LEFT`, ещё `545` — с `MANAGER`; ни один вход не был полноценным timed-dialogue.

### 2. [Защита неподтверждённых ролей](./TZ-02-role-attribution-guard.md)

Если роль не доказана существующим `role_mapping`, конспект собирается из закрытого безопасного набора, а обещания, отказы, оплата, возражения и next step не публикуются как факты. Обязательны review и понятная причина.

Доказательство того же снимка: `1 298/1 843` Analyse (`70,4%`) имели недоверенные роли; у `628` из них уже был next step, у `982` не было review.

### 3. [Доказательства каждого бизнес-факта](./TZ-03-claim-evidence.md)

Для оплаты, даты, суммы, класса, предмета, обещания и следующего шага модель указывает только `turn_id`. Сервис сам прикладывает точную исходную реплику и таймкод. Без valid evidence поле не становится фактом/автозадачей/частью базы знаний.

Доказательство: `evidence=[]` у всех `1 843/1 843` готовых Analyse; текущий prompt evidence конкретных полей не требует.

### 4. [Безопасная нормализация и МСК](./TZ-04-safe-normalization-msk.md)

Raw transcript никогда не переписывается. Нормализованное значение хранится отдельно с raw, claim, tenant, rule ID и версиями engine/ruleset. Используется существующий normalizer, fuzzy/LLM-замены запрещены. Время переводится общим `ZoneInfo("Europe/Moscow")` formatter один раз; дата/менеджер удаляются из текста конспекта.

Доказательство: `1 843/1 843` history summaries содержали точный UTC-префикс, `0/1 843` — соответствующий МСК-префикс.

### 5. [Версионированный Google-публикатор](./TZ-05-versioned-google-publisher.md)

Один checked-in скрипт становится единственным writer A:P. Он строит желаемые 16 колонок для всех готовых Analyse, обновляет stale строки, полностью сверяет лист, сортирует целые строки и подтверждает запись только после readback. Два маленьких реестра в той же SQLite хранят call key/номер/verified hash и устойчивый incident для неопознанной физической строки; новой базы нет.

Сохраняются требования Дмитрия:

- свежие звонки сверху;
- МСК;
- `2 мин 23 с`;
- J переносится и определяет высоту;
- P содержит полный transcript, но визуально `CLIP` и не раздувает строку;
- Q:Y после операции пусты.

Доказательство: среди `673` однозначно связанных Google-строк `53` имели устаревшую собственную проекцию; `0` были доказанным конспектом другого звонка. Значит доказана stale-проблема, а не массовый sort shift.

## Что уже сделано и не делается заново

- Whisper/GigaAM/Resolve уже сохраняют варианты, dialogue lines и role mapping.
- GigaAM уже ускорен безопасным режимом official 0.2 + прежняя v2 RNNT + batch=4; это не часть пяти новых ТЗ.
- Google уже умеет формат длительности, МСК, newest-first, J/P layout; эти правила переносятся в код без изменения смысла.
- Существующий tenant normalizer и frozen corpus переиспользуются.
- Customer Timeline, dedupe/supersession и importer уже существуют; новую базу знаний проектировать не нужно.

## Термины

- `raw transcript` — исходная сохранённая расшифровка; её не переписываем.
- `DialogueInput` — упорядоченные реплики одного звонка с `turn_id` и таймкодами.
- `claim` — один бизнес-факт, связанный с конкретными репликами этого же звонка.
- `role guard` — решение `trusted/untrusted/not_applicable`, разрешающее или запрещающее атрибуцию сторонам.
- `projection` — ровно 16 видимых значений A:P для Google.
- `transport_go` — доказано, что строка правильно связана/записана; содержание ещё может быть legacy.
- `content_quality_go` — доказано, что содержание прошло v3 claims, role/time/normalization gates и аудиопроверку.
- `identity_quarantine` — физическую Google-строку нельзя однозначно связать со звонком; любые write/sort блокируются.
- `data_quarantine` — звонок связан, но его новая проекция невалидна; остальные однозначные строки могут публиковаться.

## Как внедрять в будущем

Это пять ТЗ, но один управляемый выпуск качества:

1. Реализовать ТЗ-01 и ТЗ-02 под выключенным флагом, не отдавая новые payload старому Google-writer.
2. Добавить ТЗ-03 и доказать полезную coverage, а не формальное массовое обнуление.
3. Добавить ТЗ-04 в shadow и принять каждое правило.
4. Реализовать ТЗ-05, сделать полный bootstrap dry-run рабочего листа.
5. Production-cutover выполнить одним совместимым комплектом ТЗ-01…ТЗ-05. Альтернатива — сначала отдельно доказать compatibility-режим ТЗ-05; режима «новый Analyse + старый writer» быть не должно.
6. Канарейка новых звонков без массового reset.
7. После общего GO — один исторический повтор Analyse из сохранённых dialogue lines; ASR/GigaAM/Resolve не запускать заново.
8. Google обновляет stale строки по fingerprint партиями.
9. Только доказанные facts передаются существующим импортёром в Customer Timeline.

Нельзя выполнять пять отдельных массовых пересчётов.

Важно: у публикатора два разных результата. `transport_go` означает только «строка Google связана, отсортирована и записана правильно»; legacy-конспект при этом ещё может оставаться старым. Массовая проблема конспектов считается решённой только после `content_quality_go`: весь целевой scope повторно проанализирован по v3, J собран из valid claims, legacy/stale=0 и пройдена ручная аудиопроверка.

## Общие STOP-условия

- факт/конспект другого звонка;
- ложная оплата, сумма, дата, обещание или сторона в verified output;
- изменение raw transcript/evidence;
- скрытая догадка вместо review;
- Google write без exact readback;
- два publisher одновременно;
- неопознанная physical row и продолжающаяся сортировка/write;
- старый Google-writer получил новый Analyse payload;
- publisher/Analyse не успевают за устойчивым входящим потоком;
- production-код или службы изменены без отдельного разрешения Дмитрия.

## Бизнес-смысл

Самый быстрый видимый эффект даст новый Google-публикатор, но включать его первым бессмысленно: он будет очень надёжно публиковать старые ошибки Analyse. Первые четыре ТЗ делают выводы безопаснее; пятый гарантирует, что именно эти новые выводы находятся в правильной строке.

Для будущей продажи главный результат — не «ИИ всегда прав», а воспроизводимая цепочка:

`звонок → точная версия диалога → конкретный факт → конкретная реплика/таймкод → правило нормализации → конкретная Google/KB-проекция`.

Ограничение честно сохраняется: evidence доказывает происхождение из transcript, но окончательной проверкой спорных денег, дат, имён и обязательств остаётся аудио.

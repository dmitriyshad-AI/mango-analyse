Несовпадение или грязное дерево — STOP. Чужой worktree не использовать, незакоммиченные

## 2. Снять правду о живом M1 (только чтение, ничего не менять)

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python3 scripts/skills/live_truth.py --no-write
launchctl print gui/$(id -u)/com.mango.calls-process-a
launchctl print gui/$(id -u)/com.mango.calls-process-b
```

Зафиксировать письменно и приложить к отчёту: фактический HEAD живой службы, PID, cwd,
загруженный SHA, файл plist, интервалы. Это будущая точка отката — без неё откат
делать не на что.

Отдельно зафиксировать **фактические переменные окружения** запущенной службы. Причина:
`worker_environment()` жёстко задаёт `RESOLVE_LLM_PROVIDER=off` и `ANALYZE_PROVIDER=codex_cli`,
но **не** переопределяет `ANALYZE_PROMPT_PROFILE`, `ANALYZE_ESCALATE_FULL_ON_AMBIGUITY`,
`TELEGRAM_NON_CONVERSATION_ADVISORY` и (в обычном service-режиме) `LLM_CACHE_ENABLED` —
они наследуются от родительской оболочки. Значение этих четырёх переменных прямо влияет
на расход, поэтому в каждом отчёте о расходе они указываются явно.

**Исполнять только штатную M1-службу через `calls_two_processes.py`.** Старый GUI и
`scripts/build_mango_new_calls_asr_ra_batch.py` пока отдельно задают
`RESOLVE_LLM_PROVIDER=codex_cli`; их запуск обойдёт экономию Resolve и нарушит бюджет.
Эти два пути — STOP до отдельной кодовой правки и проверки.

Дополнительно read-only:

```bash
sqlite3 <рабочая_БД> 'PRAGMA query_only=ON;
  SELECT COUNT(*) FROM pragma_table_info("call_records") WHERE name="source_recording_id";'
sqlite3 <рабочая_БД> 'PRAGMA query_only=ON;
  SELECT source_recording_id, COUNT(*) FROM call_records
  WHERE source_recording_id IS NOT NULL AND source_recording_id <> ""
  GROUP BY 1 HAVING COUNT(*) > 1;'
```

Первый запрос отвечает, есть ли столбец. Если он вернул `0`, столбца ещё нет — второй
запрос **не выполнять**, sqlite ответит `no such column`, и это не признак поломки:
столбец добавит штатная миграция `init_db()` при первом запуске нового кода.

Если первый запрос вернул `1`, второй обязан вернуть пусто. Любой дубль непустого
`source_recording_id` — STOP до разбора связи. Учесть заранее: при дубле миграция
`init_db()` сама останавливается с ошибкой `duplicate source_recording_id blocks database
migration` (`src/mango_mvp/db.py:111`) и уникальный индекс не создаётся — то есть новый код
на такой базе просто не стартует, пока связь не разобрана. Рабочую БД руками не
редактировать.

## 4. Доработка захвата — обязательна до первого реального звонка

Без неё все звонки останутся недоверенными: проверка вернёт `provider_evidence_missing`,
в отчёте не будет результата, возражения, следующего шага и срока. Это не дефект, это
порядок работ.

Минимум, который M1 обязан встроить в существующий capture:

1. Читать transcript Mango пакетами не более 500 `recording_id` через
   `MangoOfficeClient.fetch_recording_transcripts()`; каждую запись разбирать отдельно
   через `parse_recording_transcripts_response()`.
   Формат запроса нестандартный: значение `recording_id` — **строка с сериализованным
   массивом**, то есть `{"recording_id":"[\"ID\"]"}`, а не `{"recording_id":["ID"]}`.
2. Полное тело пакетного ответа сохранить **один раз** owner-only по SHA-256
   (`<capture_root>/<sha256>.json`, каталог `0700`, файл `0600`, атомарно, без симлинков
   и облачной синхронизации). В строку звонка общий пакет с чужими разговорами не
   копировать: в per-call evidence кладётся только конверт своего `recording_id`,
   SHA списка фраз и ссылочный `batch_response_sha256`.
3. `recording_id` проверять по неизменяемым метаданным capture и хранить в отдельном
   столбце `call_records.source_recording_id`, а не внутри изменяемого JSON.
4. Не доверять `channels`, порядку каналов, имени файла, приветствию и направлению
   звонка. Внутренний звонок (два сотрудника) — всегда недоверенный.
5. Evidence писать условным обновлением: только если `id`, `source_call_id`,
   `source_recording_id` и прежний `transcript_variants_json` совпадают с прочитанным
   снимком. `rowcount != 1` = гонка и карантин, а не повторная безусловная запись.
   При первом новом evidence в `pending` переводятся только производные статусы
   Resolve/Analyse/sync; аудио, Whisper, GigaAM и прежние результаты не трогаются.
6. Повтор с тем же evidence SHA обязан быть пустым: 0 обновлений, 0 Resolve, 0 Analyse,
   0 обращений к модели.
7. Rescue-ASR не имеет права заменить provider evidence.

Первое реальное сырое тело ответа Mango приложить к отчёту. Если форма отличается от
ожидаемой — остановиться и расширить parser отдельным тестом, **не угадывать**.

## 5. Лестница проверки

Каждая ступень — только после зелёного отчёта предыдущей и отдельного разрешения
Дмитрия на реальное чтение и обработку.

| Ступень | Что делаем | Что должно получиться |
|---|---|---|
| 0. Офлайн | разделы 1–3 | тесты зелёные, дублей `source_recording_id` нет, правда о живом M1 записана |
| 1. Один звонок | обычный двусторонний звонок с раздельными дорожками | ни одна реплика не исчезла и не переставилась; роли совпали с аудио; каждый рискованный вывод имеет ссылку на реплику |
| 2. Повтор того же звонка | ничего не менять и запустить снова | служба: `status=idle`, `stop_reason=unchanged_snapshot`, `new=0`, `reused=1`, `runs_resolve_analyze=false`. Отдельно прямой повтор Analyse: `cache_hit=true`, 0 обращений к модели |
| 3. Десять звонков | обычный диалог, входящий/исходящий, один голос, автоответчик, шум, перебивания, длинная запись, неоднозначные дорожки, оплата, явное отрицание оплаты | каждый сверен вручную; доля эскалаций compact→full измерена |
| 4. Калибровка 50 | 50 вручную проверенных разговоров разных типов; список ID и правила отбора заморожены **до** чтения результата | матрица ошибок по типам; пороги ролей меняет только Дмитрий по этому отчёту |
| 5. 50 доверенных + 50 недоверенных | выборка не пересекается с калибровочными 50 | у доверенных — точность ролей и ссылок; у недоверенных — 100% «Спикер A/B», 0 коммерческих выводов, **0 обращений к модели** |
| 6. Двести | стратификация по менеджерам, длительности, направлению, качеству аудио, типу разговора | отчёт для РОПа + технический отчёт без телефонов и текста разговоров |

Между ступенями 2 и 3 никаких «заодно прогоним сотню». Ступень 6 не запускается, пока
Дмитрий не согласовал бюджет по числу обращений к модели.

## 6. Отчёт по расходу на каждой ступени

Единица бюджета — **число обращений к модели**, не токены: Codex CLI точные токены не
возвращает и система честно пишет `unavailable`. Оценивать токены по символам запрещено.

Это правило **отменяет** формулировку «отчёты ступеней с расходом токенов» в справочном
`M1_QUALITY_V3_INTEGRATION_PROMPT.md`: требовать токены от Codex-пути нельзя, их некому
сообщить.

В каждом отчёте:

- `RESOLVE_LLM_PROVIDER`, `ANALYZE_PROVIDER`, `ANALYZE_PROMPT_PROFILE`,
  `ANALYZE_ESCALATE_FULL_ON_AMBIGUITY`, `LLM_CACHE_ENABLED`,
  `TELEGRAM_NON_CONVERSATION_ADVISORY` — фактические значения запуска;
- звонков всего; из них: недоверенные (0 вызовов), детерминированно несодержательные
  (0 вызовов), попавшие в кэш, реально вызвавшие модель;
- обращений `compact`; обращений `full` (эскалация) и их доля от доверенных;
- обращений Resolve к модели — обязан быть 0;
- по каждому сочетанию `provider/model/prompt_version`:
  `exact + partial + unavailable = model_calls`, `model_usage_balanced=true`,
  `identity_balanced=true`;
- журнал `analysis_attempts_json`: уникальные `attempt_id`, ни одной записи в состоянии
  `reserved` или `indeterminate`.

Целевой бюджет по ступеням (предложение к утверждению Дмитрием) — в
[M1_FINAL_ACCEPTANCE_CHECKLIST_2026-08-17.md](./M1_FINAL_ACCEPTANCE_CHECKLIST_2026-08-17.md),
раздел «Бюджет».

## 8. Что запрещено включать до отдельной приёмки

**Запрещено всегда, до отдельного решения Дмитрия по каждому пункту:** массовый повтор
истории; `--execute` Google-выгрузчика; оба пути записи в AMO (`deal_dossier` и
`sync_amocrm`); Tallanto; live Customer Timeline; установка launchd; слияние в `main`.

**Запрещено по умолчанию, открывается пошагово:** любое обращение к реальным данным —
скачивание записей из Mango API, распознавание, Resolve и Analyse живых звонков. Каждая
ступень раздела 5 требует **своего** разрешения Дмитрия; разрешение на ступень 1 не даёт
права запускать ступень 3. Разделы 1–3 (worktree, чтение правды о службе, офлайн-тесты)
разрешения не требуют: они ничего не читают из Mango и ничего не пишут наружу.

## 9. Жёсткие условия остановки

Остановиться немедленно и ничего не публиковать, если:

- пропала или переставилась хотя бы одна реплика;
- «Менеджер/Клиент» появились без связанного с этим звонком ответа Mango;
- provider evidence можно перепривязать к другому `recording_id` или `source_call_id`;
- два звонка имеют один непустой `source_recording_id`;
- рискованный вывод опубликован без точной ссылки на реплику;
- недоверенный звонок получил коммерческий вывод или вызвал модель;
- повтор вызвал модель или создал дубль;
- баланс не сходится, либо в журнале попыток есть незакрытая, неопределённая или
  повторная запись;
- найден второй Google-writer или два владельца службы одновременно;
- в логе или инциденте оказался телефон, почта или текст разговора.

## 10. Откат

1. Остановить обработку, дождаться завершения текущего звонка.
2. Вернуть worktree M1 на прежний зафиксированный SHA, снятый в разделе 2.
   Документированная база сравнения — `c18ca4c830b9ac122363b2369567add37a11ca8d`;
   **фактический SHA живой службы берётся из отчёта раздела 2, а не из этого файла.**
3. Данные не откатывать: аудио, оба ASR-результата, исходные реплики и прежние
   результаты не изменялись. `source_recording_id` — штатная аддитивная миграция,
   старому коду не мешает.
4. Кэш не чистить.
5. К отчёту приложить: причину, SHA до и после, состояние очереди, число звонков в
   промежуточных статусах, подтверждение что внешних записей не было.

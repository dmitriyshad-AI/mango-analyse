# P08: инвентаризация P0 без изменения поведения

## Цель

Зафиксировать владельцев, callers и различия P0-наборов и логических парсеров.
Ничего не объединять до парного экзамена M1.

## Приёмка

- Для каждого кандидата есть файл:строка, callers, входы и различия.
- Latch/history и локальные текстовые реализации не названы дублями без
  доказательства одинаковой границы смысла.
- Сформулирован минимальный парный экзамен M1.
- Существующие P0-тесты зелёные; независимый архитектор и бизнес-аудитор дали
  вердикт.

## СТОП

- Не менять живой код, P0-маршрутизацию, regex, флаги и данные.
- Не запускать LLM локально.

## Итог инвентаризации

### Владельцы P0

1. `p0_recall_spec.py:13-15` — канон распознавания P0 в текущем тексте.
   Он содержит `refund`, `legal`, `complaint`, `payment_dispute` и вызывается
   общими входными и выходными защитами.
2. `dialogue_memory.py:144-145` — два одинаковых по значениям, но разных по
   смыслу набора. `HARD_P0_LATCH_CODES` удерживает активный риск между ходами,
   `HARD_P0_HISTORY_CODES` навсегда отмечает, что реальный P0 уже был.
3. `output_verification_floor.py:587` — читатель уже собранной памяти перед
   ответом. В нём есть `refund_claim` и `p0`, а обычный `refund` обрабатывается
   отдельно с исключением для безопасного вопроса до оплаты.
4. `reliable_answerer.py:588-622` — локальный стоп только для улучшателя
   Step1. Он учитывает текст, результат модели, метаданные, воронку и память.
   Это не общий классификатор P0.
5. `p0_recall_spec.py:180-195 P0_HARD_TEXT_MARKERS` — живых вызывающих нет:
   только определение и снимок теста. Не делать его источником истины.

### Логические преобразователи SemanticFrame

- `provider.py:1757-1771` и `policy_routing.py:2367-2381` совпадают по
  поведению на `None`, bool, числах и строках. Это кандидат на отдельное
  механическое объединение с сохранением прежних имён.
- `text_hygiene.py:713-722` имеет другой контракт: не принимает числовые
  `0/1` и строки `y/n/on/off`. Объединение изменит P0-текст и условия
  `must_handoff`, поэтому запрещено без отдельного M1-экзамена.

### Найденные смысловые риски

1. Канонический `p0_pre_gate` распознал 50/50 положительных P0-примеров и
   дал 0 ложных P0 на каноническом безопасном наборе.
2. Локальный `_has_p0_signal` улучшателя, вызванный без заранее выставленных
   флагов, пропустил 45/50 тех же P0-примеров. Верхние защиты обычно страхуют,
   но порядок слоёв нельзя считать вечной гарантией. Нужен отдельный фикс,
   который переиспользует канон и сохраняет проверки метаданных/памяти.
3. `_is_benign_presale_refund_question` может принять постоплатный запрос с
   цитатой «перед оплатой спрашивали» за безопасный вопрос до оплаты. Нужен
   регрессионный пример и проверка факта уже совершённой оплаты.
4. При включённом модельном P0-фильтре часть жалоб на сервис может сниматься,
   если не попала в локальный backstop. Это проверяется только полным путём.

### Проверка

- Независимый архитектурный аудит: PASS, механическая унификация наборов
  запрещена.
- Независимый бизнес-аудит: PASS_WITH_NOTES, два P1-риска выше вынесены в
  обязательный следующий пакет.
- Целевые тесты: `55 passed in 0.85s`.
- Код, P0-маршрутизация, флаги, данные и внешние системы не менялись.

## Парный экзамен M1 перед P0-правками

Сравнить текущую основу и кандидата на полном живом пути:

- Wappi 200;
- Risk31 с тремя независимыми оценками;
- память OFF/ON по 20 сценариев;
- все 50 `P0_TRUE_POSITIVE_CASES` и весь `P0_BENIGN_CASES`;
- отдельные сценарии: возврат до и после оплаты, постоплатный запрос с цитатой
  «перед оплатой», спор платежа, юридическая угроза, жалоба на сервис,
  безопасность ребёнка, старый P0 с активной и снятой памятью.

Обязательная приёмка: все настоящие P0 уходят только менеджеру; потеря P0,
смешение брендов, утечка ПДн и выдуманные факты равны нулю; безопасные вопросы
до оплаты не начинают массово уходить менеджеру; трассы показывают источник
P0, состояние памяти и причину отключения улучшателя.

- Нетестовый код: добавлено 0 строк, удалено 0 строк.
- Новые файлы кода: 0; новые флаги: 0; новые зависимости: 0.

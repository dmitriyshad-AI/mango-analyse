# Безопасная плановая проверка publisher звонков без Codex

Шаблон ручной теневой проверки `scripts/publish_live_mango_calls_google.py`.
В нём намеренно нет ни `--execute`, ни расписания: он не пишет в Google/SQLite,
но теневой прогон авторизуется и читает текущий Google-лист для сверки. Это не
офлайн-режим. Ничего не установлено, `launchctl` не вызывался. Плановую задачу
владелец создаёт отдельно только после подключения алертов и разрешения на
эксплуатацию.

## СТОП для M1 live

До запуска на M1 обязательны два условия, и ни одно из них не выполнено этой
задачей:

1. в конфиге заданы владелец инцидентов и приёмник алертов (owner/sink); транспорт
   алертов в коде **не подключён** — сейчас единственный сигнал это код выхода и
   JSON в stdout, поэтому без внешнего мониторинга инцидент никто не увидит;
2. доказано, что writer ровно один: скрипт держит файловый lock из конфига, но это
   доказывает единственность только среди процессов, которые берут **тот же**
   lock-файл. Старый natural-language writer и любые ручные правки листа должны
   быть остановлены и подтверждены владельцем до первого `--execute` на M1.

## Что подставить

| Плейсхолдер | Значение |
|---|---|
| `__PYTHON__` | абсолютный путь интерпретатора, которым идут тесты репозитория |
| `__REPO__` | абсолютный путь рабочего дерева с зафиксированным HEAD |
| `__CONFIG__` | owner-only JSON конфиг publisher (`chmod 600`), вне git |
| `__LOG_DIR__` | owner-only каталог логов (`chmod 700`), вне git |

## Граница проверки ревизии (честно)

`expected_code_sha` сверяется с HEAD, и грязное дерево запрещено, **только в
режимах `--execute` и `--bootstrap`**. Сухой прогон (без флагов) намеренно не
требует ни `expected_code_sha`, ни чистого дерева: он ничего не пишет ни в
Google, ни в SQLite, и должен оставаться доступным во время разработки. Поэтому
«сухой прогон прошёл» не является доказательством того, что боевой прогон
запустится с этим же деревом — проверку ревизии даёт только сам `--execute`.

## Порядок владельца

1. Теневой сетевой прогон без записи: `__PYTHON__ scripts/publish_live_mango_calls_google.py --config __CONFIG__`.
2. Разовый bootstrap состояния по фактическому листу (`--bootstrap --confirmation BOOTSTRAP_MANGO_CALLS_LIVE`).
3. Подключить внешний приёмник ненулевого кода выхода и подтвердить тестовым
   сбоем, что ответственный действительно получил уведомление.
4. Провести ручной боевой прогон отдельной явной командой с `--execute` только
   после разрешения Дмитрия.
5. Только после зелёного readback владелец может локально создать отдельный
   monitored execute-plist. Этот репозиторный шаблон в боевой writer не
   превращается и остаётся безопасной сухой проверкой.

## Коды выхода для мониторинга

| Код | Значение |
|---|---|
| `0` | `health.status=green`: открытых инцидентов данных нет |
| `2` | прогон прошёл, но `health.status=amber/red`: есть открытые инциденты (`amber`), либо инцидент старше SLA 24 ч (`red`). Валидные строки при этом опубликованы |
| `1` | прогон остановлен исключением: ошибка идентичности локальных строк, нераспознанная физическая строка листа, расхождение readback, испорченное состояние или ошибка Google/БД |

### Важно про код `1`

`1` **не** означает «записи не было». Он означает только «прогон не дошёл до
конца». Если исключение произошло **после** отправки `batchUpdate` в Google
(потеря ответа, таймаут, расхождение readback), запись в лист уже могла
примениться. Ошибки идентичности и ошибки распознавания физических строк
происходят до `batchUpdate` и записи не дают, но по коду выхода эти случаи
неразличимы.

Поэтому после `1` разрешён **только** повторный запуск того же идемпотентного
publisher/recovery: он видит зарезервированную строку, сверяет её точный хеш и
сам закрывает незавершённую запись. Ручная правка листа, ручной повтор
`batchUpdate`, удаление состояния или запуск второго writer запрещены — они
ломают восстановление.

Отчёт печатается в stdout одной JSON-строкой (`status`, `health`, `data_errors`,
`data_error_codes`) и не содержит текстов разговоров и телефонов. Инциденты
хранятся в owner-only JSON sidecar из конфига с устойчивым обезличенным ключом
(стабильный `call_key`, не локальный id SQLite); в рабочую SQLite новых таблиц
publisher не добавляет. Старый sidecar со схемой `state_v1` и полем
`data_errors` читается и мигрируется в `incidents` без потери ошибок.
